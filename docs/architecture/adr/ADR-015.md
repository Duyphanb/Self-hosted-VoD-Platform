# ADR-015: Search and discovery

Status: Proposed on 2026-11-28 for #128. The owner chose accent-insensitive search with aliases (2026-11-03,
confirmed 2026-11-26), kept provider text out of the index, kept published titles without playable media in the
results, limited filters and similar titles to the admin's own data, and approved the rule-based recommendation set
(2026-11-25 and 2026-11-26). The mechanisms (normalizer, tables, locks, tiers, queries, routes) are the author's
proposal for approval in this pull request, which also records an independent review. The package becomes the frozen
decision when the owner merges it. `main` has no search code yet; the other documents describe their current state,
and their sections marked "planned (ADR-015)" describe the target.

## Context

The search side of the catalog exists only on paper at `1892c5c`:

- `backend/search` contains only `package-info.java`. `movies.search_vector` (`V1__init_schema.sql:43`, GIN index at
  `:152`) is never written (`MovieService.java:65-66`).
- The contract declares `GET /api/v1/search` and `GET /api/v1/search/suggestions` (`API-CONTRACT.yaml:954-1001`) with a
  `q` of `minLength: 1`, no maximum and no 400 response. Results are `MovieSummary` items (`:1819-1830`) and
  suggestions are plain strings (`:1832-1841`). #128 found what a direct implementation would do: `to_tsquery` on raw
  input answers 500 for `a & (`, an unescaped `ILIKE` treats `%` and `_` as wildcards, an order by `ts_rank` alone has
  no total order, so pages repeat or skip rows, and a person or genre suggestion can reveal the cast of an unpublished
  movie.
- `SEQUENCE-DIAGRAMS.md:352-378` draws a Redis search cache, which would keep serving an archived title until the entry
  expires.
- Catalog writes that change searchable values (movie create and update, genre and person rename) run through
  `CatalogWriteRetry` (`MovieService.java:109-152`, `GenreService.java:84-88`, `PersonService.java:85-94`), which runs
  each attempt in a new transaction (`CatalogWriteRetry.java:72-99`). Archive is a status change outside it
  (`MovieService.java:310`).
- The ADR-009 slug rule removes every combining mark (`SlugNormalizer.java:31,47`), so it merges が and か; slugs also
  drop every character outside `a-z0-9`. It cannot serve as a search key.
- Compose's Flyway owner role has `CONNECT` on the database and `USAGE, CREATE` on schema `public` only
  (`deploy/postgres-init.sh:93-100`), so it cannot create an extension. Reproduced during this design (2026-11-26) in a
  disposable container of the CI image (`postgres:16-alpine`, ICU `vi`): `CREATE EXTENSION pg_trgm` and `unaccent`
  fail with "permission denied". Testcontainers runs Flyway as a superuser, so a migration that creates an extension
  passes the backend tests and fails in Compose.
- Also reproduced in that container, on a synthetic catalog of 500 titles, 2,666 names and 50 franchises: the
  `simple` parser makes `進撃の巨人` one lexeme, so full-text search never matches `葬送` inside `葬送のフリーレン`;
  `spiderman` does not match `Spider-Man`; an always-on trigram branch turned a two-word query into 390 hits; and the
  whole candidate query (names, full text, visibility, deduplication, count, page) ran in 1-10 ms of server time. These
  numbers support the design; they are not the NFR measurement, which #129 makes over HTTP.
- `deploy/nginx/nginx.conf` sets no `log_format` or `access_log`, and neither does the SPA's static server
  (`frontend/nginx.conf`), so both use Nginx's default format, which records the request line with its query string
  (predicted from Nginx's defaults). Nginx's error log also writes the request line when it logs an error for a
  request, for example a failed upstream connection. `Referrer-Policy: no-referrer` is set at the edge
  (`nginx.conf:37`). The backend logs only status, code and request ID for a rejected request
  (`ApiErrorFactory.java:95,106`), and no backend code logs a query string.
- [ADR-013](ADR-013.md) D10 fixes the level: search indexes titles, one card per visible title, and a visible
  franchise's name is a search name of each of its parts. Ratings and the watchlist are per title, progress and
  history per episode. It leaves the fate of `search_vector` to this ADR.

Owner decisions this ADR implements:

1. **Accent-insensitive search with aliases** (2026-11-03 on #128, confirmed 2026-11-26).
2. **Provider text is not indexed** (2026-11-26): search uses the admin's own fields, the admin's aliases and AniList
   names; TMDB-derived text stays out unless TMDB confirms that indexing is allowed.
3. **A published title with nothing playable stays in the results**, labelled "Đang xử lý" or "Chưa có tập", like the

4. **TMDB-imported genres, cast and year are not used in filters or in "Tương tự"** until ADR-014 (planned) records

5. **Light, rule-based recommendations** (2026-11-25, replacing the post-MVP decision of 2026-11-13): "Tương tự" on the

   own data. With no history there is no personal row and Home shows "Mới thêm". Reasons are text, never a percentage
   (2026-11-26). Friends and "% match" stay out.
6. **Home also carries up to three pinned collections** (2026-11-26, ADR-021, planned) and, after its gate, the
   worldwide trending row (2026-11-26, ADR-014, planned). The approved roadmap (2026-11-26) gives this ADR the Home row
   order.
7. **`info.version` stays `1.0.0-frozen`**, and the contract describes the change (roadmap approval, 2026-11-26,
   resolving the #128 and #130 conflict).

## Decision

### D1 What search returns, to whom

- **A hit is one title**, a part of type `MOVIE`, `TV_SEASON`, `OVA`, `ONA` or `SPECIAL` (ADR-013 D1), never a
  franchise and never an episode. Several names of one title that match give one hit.
- **Eligibility is title visibility** (ADR-013 D3): a title is a candidate exactly when it is `PUBLISHED`, for every
  role. Admins find hidden titles in the admin list, not in search. Every discovery query (search, suggestions, similar
  titles, the personal row) uses catalog's one visibility check, and counts exclude hidden titles before paging.
- **A visible title is a hit whatever its availability.** The card is the catalog's title summary, so its
  `availability` (ADR-013 D11) drives the label exactly as in the catalog list: `PROCESSING` shows "Đang xử lý",
  `UNAVAILABLE` shows "Chưa có tập", `PLAYABLE` shows none. The strings live in the UI string table (UI-BRIEF).
- **A franchise name matches only while the franchise is visible.** A hidden franchise's name never matches, never
  appears as `matchedName` and never appears on a card.
- **Not searchable:** episode names and synopses, franchise descriptions and every provider description. Episode texts
  would mostly come from TMDB, which is not indexed (D11); they can join with an explicit need.
- **Cards come from the catalog's batch summary path** (today `MovieService.summaries`, `MovieService.java:234`), so
  search never re-implements visibility or card fields and follows ADR-013 and #130 automatically.
- **Ownership.** Catalog owns aliases (table, rules, admin endpoints) and the indexing port (D5). The search module owns
  the normalizer, the search tables, the indexer, the reconciler, search, suggestions and the discovery endpoints of
  D12 and D13. Discovery reads progress, history and ratings with set-based SQL, as Continue Watching reads catalog
  tables today (`ContinueWatchingReader.java:23-24`), through the catalog visibility check and ADR-013's one
  definition of the active asset. No new module and no Maven cycle: search depends on catalog only.

### D2 Text normalization (`SearchText`, version 1)

One pure Java function, versioned and unit-tested without a database, produces every stored key, every document text
and every query key. It iterates code points, never UTF-16 units or a Latin range expression.

- **Exact key:** remove format characters (Unicode category `Cf`, for example a zero-width space or a soft hyphen);
  apply NFKC; lower-case with `Locale.ROOT`; collapse each run of white space to one space; trim. Diacritics and
  punctuation stay, so "Hài" and "hải" differ at this level.
- **Folded key:** the exact key, decomposed (NFD); each combining mark whose base character is in the Latin script
  removed; then `đ` → `d`, `ß` → `ss`, `æ` → `ae`, `œ` → `oe`, `ø` → `o`, `ł` → `l`, `ı` → `i`; recomposed (NFC); each
  run of characters that are not letters, digits or marks (categories `L`, `N`, `M`; kana and kanji are letters)
  replaced by one space; trimmed. Marks on non-Latin bases stay, so が and か remain different, and dakuten survive.
- **Compact key:** the folded key without spaces, so `spiderman` meets `Spider-Man` and `onepiece` meets `One Piece`.
- **Names without letters or digits.** A name whose folded key is empty (a title made only of symbols) matches only by
  its exact key (tiers 1 and 2 of D7) and never takes part in a prefix, substring or score computation; such a title is
  best given an alias with letters.
- **Bounded keys.** Each key keeps at most its first 300 code points, the query bound (D6), so every key fits a B-tree
  entry (at most 1,200 bytes against PostgreSQL's limit of about 2,700). Only an extreme NFKC expansion of a
  255-character name reaches the cap, and such a name then matches on its first 300 code points.
- **Version.** Each derived row stores the `index_version` that built it. Any change of the rules, of the document
  builder (D4) or of the JDK's Unicode tables that changes an output bumps it; a unit test pins the outputs of a fixed
  sample, so a JDK upgrade that changes them fails CI until the version is bumped.
- Kept out on purpose: hiragana and katakana folding, kanji variants, transliteration, stemming and Vietnamese word
  segmentation. Aliases cover those cases by hand, entered by the admin or imported from AniList.

Reproduced during this design with a JDK 21 sketch of these rules: `Đất Rừng Phương Nam` → `dat rung phuong nam`, an NFD
`Pháp sư tiễn táng` → `phap su tien tang`, `ガギグ パピ` unchanged, `ＡＢＣ　１２３` → `abc 123`, `ｶﾞﾝﾀﾞﾑ` → `ガンダム`,
`İstanbul` → `istanbul`, `Straße` → `strasse`, `Shingeki no Kyōjin` → `shingeki no kyojin`.

### D3 Aliases

- **`title_aliases`** (catalog, created by SR-1): `id`, `title_id` (foreign key to `titles`, cascade), `name`
  (1-255 characters, trimmed with white space collapsed and control characters rejected, like genre and person names),
  `locale` (optional BCP 47 tag, at most 35 characters), `kind` (`ORIGINAL`, `LOCALIZED`, `ROMAJI`, `NATIVE`,
  `ENGLISH`, `SYNONYM` or `OTHER`; `OTHER` when omitted), `created_at`; unique on `(title_id, name)`. An alias is
  unique within its title, never globally: remakes and seasons share names.
- **Admin API:** `GET` and `PUT /api/v1/admin/titles/{titleId}/aliases`, for a title in any status (ADR-013 D3 admin
  exception; 404 when it does not exist, with `MOVIE_NOT_FOUND` until ADR-013 S2 renames it to `TITLE_NOT_FOUND`). `PUT`
  replaces the list: at most 20 aliases; two entries with the same normalized name are 400 `VALIDATION_ERROR`. An alias
  whose name is unchanged keeps its row and ID, so the provenance ADR-014 attaches to it (ME-1) survives an unrelated
  edit; ME-1 decides how a changed `kind` or `locale` affects provenance. Responses list aliases by name (ICU `vi`),
  then ID.
- **Concurrency.** The `PUT` runs through `CatalogWriteRetry` (with its lock, D5) and locks the title row; the last
  write wins until ADR-014 adds the title revision and its 409.
- **Import.** ME-4 (#246) imports AniList names as aliases; #245 stores TMDB names as aliases with a TMDB origin, which
  the index excludes (D11). The provenance columns (`origin` and the rest) are added by ME-1 (ADR-014); SR-1 creates
  only the base columns above.
- The UI shows an original or romaji name as a card's second line (UI-BRIEF). The field that carries it and the choice
  among several aliases are added by the UI slice that first shows it.

### D4 Search data

Search owns two derived tables; catalog owns every fact they are built from.

- **`title_search_names`**, one row per searchable name: `id`; `title_id` (foreign key to `titles`, cascade) for a
  display title or alias row; `source` (`DISPLAY_TITLE`, `ALIAS`); `alias_id` (foreign key to `title_aliases`,
  cascade; set exactly for `ALIAS`); `name` (the original text, returned as `matchedName`); `exact_key`, `folded_key`
  and `compact_key` (`text COLLATE "C"`); `index_version`. B-tree indexes on each key and on `title_id`. A `COLLATE "C"`
  B-tree serves equality and anchored prefix matching (reproduced); substring matching scans the table, which held
  2,666 rows in the design's synthetic catalog and stayed within its 1-10 ms. S3 (#262) adds franchise name rows:
  `franchise_id` (foreign key to `franchises`, cascade), the `FRANCHISE_NAME` source, and a check that exactly one of
  `title_id` and `franchise_id` is set.
- **`title_search_documents`**: `title_id` (primary key and foreign key to `titles`, cascade), `document` (`tsvector`,
  not null), `index_version`, `rebuilt_at`; a GIN index on `document`.
- **Every title has its rows, whatever its status**, so publishing needs no rebuild; visibility applies at query time.
- **Franchise names are one row per franchise**, joined to titles through `titles.franchise_id` with the franchise's
  `PUBLISHED` status at query time. A franchise status change or moving a title between franchises needs no rebuild; a
  rename rewrites one row. The franchise name never enters a title's document, which does not depend on the
  franchise's status.
- **Document content.** Folded text from `SearchText`, built in Java and sent as bound parameters, weighted with
  `setweight` on `to_tsvector('pg_catalog.simple', …)`; the schema-qualified configuration is used on both sides, so
  `search_path` cannot change it:

  | Weight | Content |
  |---|---|
  | A | display title, part label (from ADR-013 S2), indexed aliases |
  | B | names of indexed genres and of credited people (actors and directors) |
  | C | release year, when indexed |
  | D | the admin's own description |

  What is indexed follows D11. SR-1 needs only ADR-013 S1, so it may land before S2 creates `titles.part_label`; it
  then indexes the fields that exist, and S2 adds the part label to the builder and bumps `index_version`, so the
  reconciler rebuilds every title once at the first start after S2 (and S3 adds the franchise name rows the same way).
- **`titles.search_vector`** (the renamed `movies.search_vector`) and its GIN index are dropped by SR-1. Catalog tables
  carry no search column.

### D5 Keeping the search data correct

- **Port.** Catalog defines a `TitleSearchIndex` port ("titles changed", "franchise changed"), implemented by the
  search module and wired by Spring, as `VideoStatusLookup` is implemented by encoding today. Catalog tests use a
  recording fake.
- **Same transaction.** Every catalog write that changes an indexed value calls the port after flushing its source
  rows and before it commits: title create and update (display title, part label, release year, description, genres,
  credits, including people created by name-only credits), the alias `PUT`, genre rename (every title with the genre),
  person rename (every title crediting the person), franchise create and rename (S3), and later the metadata apply,
  refresh, unlink and withdrawal of ADR-014. Status changes (publish, archive, restore, at any level) and moving a title
  between franchises call nothing. The indexer reads the sources again in new statements, never from entities loaded
  earlier, rewrites the affected rows and documents, and a failure rolls the catalog write back.
- **One catalog write lock.** Each attempt of `CatalogWriteRetry` takes `pg_advisory_xact_lock` on one fixed key
  reserved for catalog writes (distinct from the `106` of `postgres-init.sh:73`) as its first statement, before it reads
  anything. No catalog write joins an outer transaction today; one that does must take the lock before that transaction
  reads a catalog row. The reconciler takes it for each chunk. Why a lock and not only row locks: under
  `READ COMMITTED`, a person rename lists the titles that credit the person while another transaction adds a credit to a
  title outside that list; the foreign-key check's `FOR KEY SHARE` lock does not conflict with the rename's update, so
  both commit and the new title keeps the old name in its document, with no deadlock for the retry to catch (predicted;
  the SR-1 race tests prove the fix). Explicit `FOR SHARE` locks on every referenced row would also close it, but every
  writer would have to remember them; one lock in the one retry wrapper cannot be forgotten.
- **Who takes it.** Every catalog write path that changes an indexed source runs through `CatalogWriteRetry`, including
  future ones (S3 franchise writes, ADR-014's apply and withdrawal job). Status-only writes, upload, progress saves and
  the worker never take the lock, and none of them waits for it while holding a catalog row, so it adds no deadlock.
  Cost: catalog writes run one at a time, which one admin does not notice. If imports later show measurable waits,
  per-source locks replace it.
- **Reconciler.** At startup, before the web server accepts requests (a `SmartInitializingSingleton`, which runs before
  Spring Boot starts the embedded server; an `ApplicationRunner` would run after it listens), the backend rebuilds
  every title, whatever its status, that has no document or whose rows carry an `index_version` other than the running
  one (older or newer, so a rolled-back backend also rebuilds), and every franchise whose name row is missing or of
  another version. It works in chunks of 100 titles, each one transaction under the lock, then checks coverage. A
  failure fails startup: the backend never serves search from a partial index. Rebuilding cannot be a SQL migration,
  because the normalizer is Java.
- **Recovery.** Deleting the rows of `title_search_documents` makes the next start rebuild every title, which is the
  repair for a projection written by a backend without the indexer (D16).
- No triggers (the ERD keeps database logic visible in application code), no Redis cache, no asynchronous indexing
  queue.

### D6 Query input

Both search endpoints apply the same rules to `q`:

- `q` is required and trimmed of Unicode white space. After trimming it holds 1 to 100 code points (counted with
  `codePointCount`, not `String.length`); blank or longer is 400 `VALIDATION_ERROR`. A control character anywhere is
  400, as in catalog text (`TextNormalizer`).
- NFKC can expand one code point into many (U+FDFA becomes 18), so a query whose exact key exceeds 300 code points is
  also 400.
- A query whose folded key holds no letter or digit (`%`, `!!!`) answers 200 with an empty result and runs no database
  query.
- Values are always bound parameters. Matching patterns are built in Java from the folded or compact key, which
  contains only letters, digits, marks and single spaces, so `%`, `_` and `\` never reach a pattern; patterns still
  carry an explicit `ESCAPE` as a defensive rule.
- Full text uses `plainto_tsquery('pg_catalog.simple', <folded q>)`, which ignores operators and punctuation and never
  raises a syntax error. `to_tsquery` never sees user input. `websearch_to_tsquery` is not used: it reads quotes, `or`
  and `-` as operators, which misreads titles with dashes.

### D7 Matching tiers and total order

For the query, `Eq`, `Fq` and `Cq` are its exact, folded and compact keys; for a name row, `E`, `F` and `C`. A query is
**substring-eligible** when `Cq` has at least 3 code points or contains a Han, Hiragana, Katakana or Hangul character.
One SQL statement combines the tiers with `UNION ALL`, keeps each title's best tier and score, joins visibility and
filters, and pages:

| Tier | Match | Score within the tier |
|---|---|---|
| 1 | `E` of the display title equals `Eq` | 1 |
| 2 | `E` of an alias equals `Eq` | 1 |
| 3 | `F` of the display title equals `Fq`, or its `C` equals `Cq` | 1 |
| 4 | the same for an alias | 1 |
| 5 | `F` of the display title or an alias starts with `Fq`, or its `C` starts with `Cq` | `len(Cq) / len(C)` |
| 6 | substring-eligible only: `F` of the display title or an alias contains `Fq` | `len(Cq) / len(C)` |
| 7 | the name of the title's visible franchise matches by the rules of tiers 1 to 6 | 1 for an equality, otherwise `len(Cq) / len(C)` |
| 8 | `document @@ plainto_tsquery('pg_catalog.simple', Fq)` | `ts_rank`, with the normalization the SR-2 fixture chooses |
| 9 | the typo fallback, only under D8 | similarity |

- **Total order:** tier ascending; score descending; then the group name (the franchise name while the franchise is
  visible, otherwise the display title) in ICU `vi` order; `franchise_order` ascending with nulls first; display title
  in ICU `vi` order; title ID. Scores of different tiers are never added or compared. The ID makes the order total, so
  pages over an unchanged catalog never repeat or skip a title, and tied parts of one franchise appear in watch order.
- **`matchedName`** is the original text of the name that gave the title its best tier and score, when that is not the
  display title: an alias (tiers 2, 4, 5, 6 and 9) or the visible franchise's name (tier 7). The display title wins a
  tie; among aliases the smallest exact key wins, then the alias ID. It is null for tiers 1, 3 and 8 and whenever the
  display title won.
- Tier 7 ranks below the title's own names, so a title found by its own name outranks a part found only through its
  franchise.

### D8 The typo fallback (conditional)

- The SR-2 relevance fixture includes a typo set (`Atack on Titan`, `Freiren`, a misspelled Vietnamese title). The
  fallback ships only if it puts the intended title in the top three for most typos with few wrong hits; the pull
  request records the result either way.
- If adopted, it uses `pg_trgm` (D16) and runs only when tiers 1 to 8 return no visible title under the same filters,
  only for a `Fq` with at least 4 letters or digits, only on display titles and aliases, with whole-name `similarity`
  (`word_similarity` lets one shared word dominate; the fixture compares both and sets the threshold). It returns at
  most 20 titles, ordered by similarity and then the tail of the total order, and the response says
  `approximate: true`. Any threshold change is `SET LOCAL`, never a session setting.
- If not adopted, no extension is installed and `approximate` is always false. Suggestions never use the fallback.

### D9 Results, filters and paging

- **Response:** `SearchResponse {query, approximate, items, page}`, where `query` echoes the trimmed `q` and each item
  is `SearchHit {title, matchedName}`; `title` is the title summary (ADR-013 D11) and `matchedName` follows D7.
- **Filters:** `genre` (normalized with the slug rule and matched on the genre slug, as in the catalog list), `year`
  and `type` (content type). Single values combined with AND, applied before count and paging; an unknown genre
  gives an empty page. D11 limits which genre and year values count.
- **Paging:** the shared `Page` and `Size` parameters (page at most 10000, size at most 100). `totalElements` counts the
  distinct visible titles that match, from its own aggregate: `count(*) OVER ()` returns no row past the last page and
  would lose the total. The page query, the count and the summary batch run in one read-only `REPEATABLE READ`
  transaction, so items and count describe one snapshot even when a title is archived meanwhile.

### D10 Suggestions

- `GET /api/v1/search/suggestions?q=` answers `{query, items}` with at most 5 suggestions,
  `SearchSuggestion {titleId, displayTitle, matchedName, contentType, partLabel, releaseYear, franchiseName}`;
  `franchiseName` only while the franchise is visible.
- Name tiers 1 to 7 only (no full text, no people, no genres, no fallback), with the input rules of D6, the visibility
  of D1 and the order of D7. No filters and no paging.
- No genre or person suggestions: a genre or person linked only to an unpublished title would reveal it (#128), and the
  genre filter covers genre browsing. Items name titles, so two titles with the same display name stay distinct, and
  selecting one opens that title by its ID; Enter opens the full results.
- The SPA (SR-3) sends nothing while an input method composes (Vietnamese Telex, Japanese IME), waits 250-350 ms after
  the last change, aborts the previous request and drops any response whose query, filters or signed-in account is no
  longer current. The combobox uses `aria-activedescendant`, and loading, empty, error and approximate ("Kết quả gần
  đúng") states are explicit.

### D11 Provider data

- Search never calls a provider, and nothing a viewer does triggers a provider call.
- **Indexed:** the admin's own fields; aliases whose origin is local or AniList; genre and credit assignments and the
  release year whose origin is not TMDB. **Never indexed:** provider descriptions (TMDB and AniList), TMDB-origin
  aliases, TMDB-origin genre and credit assignments, and a TMDB-origin release year.
- ADR-014 (planned) owns provenance: ME-1 adds the origin columns to `title_genres`, `title_credits` and
  `title_aliases` and the field provenance of the release year. Until ME-1, every row is the admin's own. From ME-1,
  the indexer filters on origin, and every metadata apply, refresh, unlink and withdrawal rebuilds the affected titles
  in its own transaction (D5).
- Because no TMDB value is ever indexed, a TMDB withdrawal never leaves a stale lexeme, and search needs no expiry
  predicate.
- **Filters and similar titles** (search filters, the catalog list's `genre` and `year`, and D12) use only values whose
  origin is not TMDB until ADR-014 records that TMDB's terms allow each use. Card display is ADR-014's decision.
- Indexing TMDB values later would be an ADR-014 decision plus an `index_version` bump; the reconciler then rebuilds.
  Provider trending (TR-1, TR-2) belongs to ADR-014.

### D12 Similar titles (RC-1, BACKLOG Issue 8.13)

- `GET /api/v1/titles/{titleId}/similar?size=` (1 to 20, default 12). The title follows the title-detail rule: 404
  `TITLE_NOT_FOUND` when it is missing or hidden, for every role.
- **Candidates:** visible titles whose `availability` is `PLAYABLE` (ADR-013 D11: a visible episode with a current
  asset, the active one from S5), other than the title itself and outside its franchise while that franchise is visible
  (the franchise strip shows those), sharing at least one genre with it. A shared person alone is not enough.
- **Data:** genre assignments and actor and director credits whose origin is not TMDB (D11).
- **Order:** shared genres descending, genre Jaccard (shared divided by the union) descending, shared people
  descending, creation time descending, ID ascending; then at most one title per franchise (the first in that order; a
  title without a franchise stands alone); then the size limit.
- **Reasons:** up to two shared genre names and up to two shared person names, from the same rows, as text, never a
  score. Both titles are visible, so a reason reveals nothing hidden.
- Response `{items: [{title, reasons: {genres, people}}]}`, empty when nothing qualifies (the page then hides the
  shelf). The same for every caller, computed on request and stored nowhere: one set-based statement plus the summary
  batch, a fixed statement count.

### D13 The personal row (RC-2, BACKLOG Issue 8.14)

- `GET /api/v1/me/recommendations`: the caller's own row only, with no user parameter, and viewer visibility for every
  role.
- **Signals:** ratings (per title, #130), watch-history completion (`completed_at`, per episode from S2, counted once
  per title) and progress rows (started). The watchlist is intent, not taste, and is no signal.
- **One seed.** Seed candidates, in order: the visible titles the caller rated 4 or 5 (rating update time descending,
  then title ID), then the visible titles of the caller's completed episodes (latest completion time descending, then
  title ID) that the caller has not rated 1 to 3. The seed is the first of the first five candidates whose row is not
  empty (below), so one isolated favourite cannot hide the row for good; with none, there is no row. Completion is a
  weak signal, because seeking to the end also sets it (ADR-011 D10), so the row names what the caller watched and
  never claims they loved it. Before #130 ships ratings, every candidate is a completion.
- **Items,** at most 12, in this order:
  1. **Next part** (`NEXT_PART`, shown as "Phần tiếp theo"): when the seed belongs to a visible franchise and the
     caller completed the seed's last visible episode (its greatest ordinal), the title with the next
     `franchise_order` in that franchise. Like the next episode (ADR-013 D4), it is never skipped: the item appears
     only when that successor is visible and `PLAYABLE` and the caller has neither started nor rated it; otherwise
     there is no next-part item and nothing about the successor leaks. Issue 8.14's "next visible, playable part"
     means this successor.
  2. **Similar** (`SIMILAR`): the seed's similar titles by D12.
- **Excluded everywhere:** the seed, every title the caller has started (a progress row on any of its episodes) and
  every title the caller has rated, so a 1 or 2 never comes back.
- **Empty rows:** a candidate's row is empty when it would hold fewer than 3 items and no next part. When every
  candidate's row is empty, or there is no candidate, the response is `{seed: null, items: []}`. A lone next part stays:
  it is the most useful suggestion there is. The row is never padded with unrelated titles.
- **Response:** `{seed: {titleId, displayTitle, reason}, items: [{kind, title, reasons}]}`, where `reason` is `RATED`
  ("Vì bạn đánh giá cao X") or `WATCHED` ("Vì bạn đã xem X").
- **Privacy:** computed on request from the caller's own rows; nothing stored, cached or logged; no cross-user signal.
  Admin Preview writes no progress or history (ADR-013 D9), so it never creates a seed. Deleting an account cascades
  its signals (ERD deletion rules). The response carries `Cache-Control: no-store`.

### D14 Home row order

Home (UI-BRIEF density A) shows these rows, top to bottom, each only when it has items:

1. **"Đang xem"**: Continue Watching (ADR-013 D8).
2. **Up to three pinned collections** (ADR-021, planned, CL-1), in their pin order, each hidden while it holds fewer
   than four visible titles.
3. **The personal row** (D13).
4. **"Mới thêm"**: the newest visible titles from the catalog list (`sort=latest`, creation time descending), labelled
   by availability like the list.
5. **Provider trending** (TR-2, ADR-014, planned), only after its gate (terms clearance and two weeks with at least
   four playable titles) and hidden below four playable titles. It comes last, so it never pushes the owner's own rows
   down.

A new viewer sees the qualifying pinned collections and "Mới thêm", with no personal row. Each row loads on its own;
one failing row shows its own error state and does not hide the others. Rows never show hidden titles and are never
padded.

### D15 Privacy, logs and caching

- **No search term in any log.**
  - The edge's access log uses one format with time, method, `$uri` (the path without its query), status, bytes,
    request time, upstream status and `$request_id`, never `$request`, `$request_uri`, `$args`, `$query_string` or
    `$http_referer`, for every location including the named error locations. The SPA's static server uses the same
    format or no access log.
  - The edge's error log writes the request line, query included, when it logs an error for a request (for example a
    failed upstream connection). The locations that receive search terms, `/api/v1/search` and
    `/api/v1/search/suggestions`, log errors only at a level that excludes these request errors (`crit` predicted to
    suffice); their failures still appear in the access log with status and request ID.
  - The SPA keeps the search page's state in the URL fragment (`/search#q=…`), which a browser never sends to a server,
    so neither Nginx nor the static server receives a search term from a page load.
  - The backend logs no request parameter. SQL and bind-parameter logging stay off. PostgreSQL logs a failing
    statement's text but, by default, none of its bound values, so `q` is only ever a bound parameter.
  - The SPA sends no search telemetry and stores no recent searches. Browser history keeps the fragment, as for any
    URL-addressable results page.
  - `Referrer-Policy: no-referrer` stays at the edge.
- **Caching.** No discovery response is cached by Nginx, the backend or Redis. `/me/recommendations` carries
  `Cache-Control: no-store`; Spring Security's default cache headers are still on (`SecurityConfiguration.java:142`
  disables only HSTS), so this is predicted to hold already, and a test asserts it.
- **Rate limiting** stays with #51.
- **Errors:** 400 `VALIDATION_ERROR`, 401, 404 `TITLE_NOT_FOUND` (similar titles, aliases) and the 503 auth-state
  response, as today; no new code.

### D16 Extensions and deployment

- **SR-1 needs no extension:** folding is Java, equality and prefix use B-trees, substring matching scans.
- **Only if SR-2 adopts the fallback:** `postgres-init.sh`, which runs as the bootstrap superuser before Flyway, also
  against existing volumes, runs `CREATE EXTENSION IF NOT EXISTS pg_trgm WITH SCHEMA public` in the application
  database and then checks the installed schema and version (`IF NOT EXISTS` alone does not); the owner keeps
  `CONNECT` only. A migration also runs `CREATE EXTENSION IF NOT EXISTS pg_trgm`, which creates it under Testcontainers
  and is a no-op for the owner role once it exists (reproduced), and adds any trigram index. The
  populated-upgrade smoke and the Compose stack smoke run Flyway as the owner role, so a migration that needs an
  extension the init step did not create fails in CI.
- `unaccent` is not used.
- **Deployment.** SR-1 deploys with ADR-013 D13's fenced sequence: writers stopped, migration, then the new backend,
  whose reconciler builds every title before it serves. Once a backend with the indexer has run, a backend without it
  must not write the catalog: its writes would leave the search rows stale with a current `index_version`. If that
  happens anyway, deleting the documents (D5) repairs it on the next start. The deployment runbook gains both steps
  with SR-1.
- Redis stays without a consumer.

## Options Considered

| Topic | Selected | Alternatives and reason not selected |
|---|---|---|
| Accent folding | One versioned Java normalizer for keys, documents and queries | The `unaccent` extension: the Compose Flyway role cannot create it, `unaccent()` is `STABLE`, so an index needs a wrapper that falsely claims `IMMUTABLE`, and the query side would need the same rules outside the database. Its default rules fold Vietnamese well (reproduced), so quality was not the reason. |
| Matching | Name tiers (exact, folded, compact, prefix, substring) plus full text | Full text alone: `simple` cannot find a Japanese partial or `spiderman`. Trigrams alone: no exact-first ranking, and noisy on short queries. |
| Typos | A fallback only when nothing matches, adopted only on fixture evidence | An always-on trigram tier: 390 approximate hits for a two-word query (reproduced). No typo handling at all without measuring: rejected by the owner's principle to decide on measured benefit. |
| Search engine | PostgreSQL | Elasticsearch or OpenSearch: another stateful service on the 12 GB VM for a catalog of hundreds of titles that PostgreSQL searches in milliseconds; revisit only if a fixture shows PostgreSQL cannot meet quality or latency. |
| Where search data lives | Search-owned name and document tables | `titles.search_vector`: one column cannot hold per-name keys or keep franchise names out of a title's document, and it puts search data in a catalog table. |
| Keeping it current | Port called in the write transaction, one catalog lock, startup reconciler | Triggers: hidden logic, and the normalizer is Java. An asynchronous queue: a stale window and a second failure mode. A one-shot backfill command run after Flyway: equivalent once, but it does not catch later version bumps. Row locks only: correct only if every writer remembers `FOR SHARE` on every referenced row. |
| Caching | None | A Redis cache: serves an archived title until it expires (#128), and PostgreSQL already answers in milliseconds. |
| Query parser | `plainto_tsquery` | `to_tsquery`: raises on user syntax. `websearch_to_tsquery`: reads quotes, `or` and `-` as operators. |
| Suggestions | Typed title items, title tiers only | Plain strings: cannot tell apart parts that share a name. Genre and person suggestions: the #128 leak. |
| Unplayable titles | Kept and labelled (owner) | Hidden from search: the catalog list shows them, so search would disagree with it. |
| Similar titles | Explainable lexicographic rules over genres and people | Weighted Jaccard over tags, studios and type: no tags or studios exist yet. Embeddings or a learned model: no data to train or judge them on. |
| Personal row | One seed, next part first, reasons as text | Several seeds: mostly repeated titles from a small catalog. A tuned affinity score (seed weights, half-life, negative penalty): nothing to tune it on. Collaborative signals or site-viewer trending: a handful of private viewers is no population, and it would expose other accounts' viewing. "% match": a number that is not a probability (owner: no). |
| Storing recommendations | Computed on each request | Stored profiles or rows: more personal data to protect and invalidate, for queries that take milliseconds. |
| Search state in the SPA URL | Fragment (`/search#q=…`) | A query string: every page load would carry the term to two Nginx servers and their logs. History state only: no bookmark or reload. |
| Search request method | `GET` with `q`, and logs without query strings | `POST` with a body: keeps the term out of URLs, but changes the frozen method for a read, and the edge still needs the log format for the other routes. |

## Consequences

- Sprint 7 search (SR-1 to SR-3, #129) and the Sprint 8 discovery rows (Issues 8.13 and 8.14) follow this ADR;
  ADR-021 and ADR-014 add their rows to the Home order of D14 and their data to D11's rules.
- Every catalog write that changes an indexed value rebuilds search rows in its transaction and runs one at a time
  under the catalog lock. Writes that bypass `CatalogWriteRetry` must not change indexed values.
- The first start after SR-1 builds the search rows of every title before the backend serves; later starts rebuild
  only missing or other-version rows.
- Search reads only PostgreSQL. A `pg_trgm` extension exists only if SR-2's fixture adopts the fallback.
- No discovery feature stores anything about a viewer. The personal row changes only when the viewer's own ratings,
  history or progress change.
- Nginx's log format, the search locations' error-log level and the SPA's fragment state ship with SR-2 and SR-3; until
  then no search route exists to log.
- Documents: ADR-009 gains an addendum; `NFR.md` NFR-010 is reworded for titles and aliases; SECURITY, ERD,
  SEQUENCE-DIAGRAMS, INFRASTRUCTURE, OBSERVABILITY, SYSTEM-ARCHITECTURE and the contract gain planned text. The
  requirement documents (BACKLOG Issues 7.4-7.7, 8.13 and 8.14, OUT_OF_SCOPE, RISKREGISTER R-010, TRACEABILITY F-016,
  F-030 and NFR-010, USERSTORIES US-012) are written by the decision-record pull request of #258.
- This document proves only the design. Relevance, timing, log and race claims need the SR and RC evidence above.
