# ADR-013: Content model: franchises, titles, episodes and asset activation

Status: Proposed on 2026-11-26 for #244. The owner chose the model, the `movies` to `titles` rename, the franchise
rule, Continue Watching per title, asset activation and Admin Preview as an exception on 2026-11-25, and the
optional admin description on 2026-11-26. The mechanisms (schema, locks, routes, migration order) are the author's
proposal for approval in this pull request, which also records an independent review. The package becomes the
frozen decision when the owner merges it. Until the implementation slices S1-S5 (D14) land, `main` keeps the movie
model, and the other documents describe it; their sections marked "planned (ADR-013)" describe the target.

## Context

On 2026-11-24 the owner decided that the catalog holds feature films, anime and multi-episode series (#244). The
chosen experience: a franchise page with a strip of all its parts in watch order, an episode grid with a part
switcher inside a part, and search results with one card per part, labelled with its type and episode count.

The schema and code at `4415d9f` know only movies:

- `movies` is both the catalog entry and the playable unit. Seven tables reference it, all `ON DELETE CASCADE`:
  `movie_genres`, `movie_credits`, `video_assets`, `playback_progress` (primary key `(user_id, movie_id)`),
  `watchlist_items` and `watch_history` (each unique per user and movie) and `ratings`
  (`V1__init_schema.sql:34-147`). No code path deletes a movie; archive is a status change.
- Ratings, the watchlist, history listing and search have no code yet: `backend/library` and `backend/search` contain
  only `package-info.java`, and `movies.search_vector` is never written (`MovieService.java:65-66`). Changing their
  level now costs documents, not data migrations.
- The current-asset rule of ADR-010 (the READY asset with the greatest `(created_at, id)` of the movie) is written
  five times: three queries in `VideoAssetRepository.java:29-61`, the Continue Watching join
  (`ContinueWatchingReader.java:24-28`) and the purge runbook query (`docs/deployment/README.md:585-603`).
- Upload and the planned retry serialize on the movie row with `FOR NO KEY UPDATE` (`MovieRowLocks.java:38-43`,
  `EncodingJobService.java:74-151`). The partial unique index `ux_video_assets_movie_in_flight` (V5) allows one
  in-flight asset per movie, and the 409 mapping matches its name (`EncodingConstraints.java:11`,
  `EncodingJobService.java:142-144`). The worker locks only asset and job rows (`WorkerJobStatus.java:195-222`) and
  never reads `movie_id`; it uses only the extension of the raw key.
- A new asset goes live the moment the worker marks it READY (ADR-010 D14), and ADR-011 D14 carries every stored
  position to it with only a clamp. The player keeps its live position across an asset change
  (`playbackRun.ts:228-239,403-413`). So an encode reaches viewers before anyone has checked it, and a different cut
  inherits positions that no longer mean the same moment.
- A progress save reads the current asset with an ordinary snapshot and then upserts (`ProgressService.java:47-58`,
  `ProgressWrites.java:21-33`). Nothing orders it against a change of the current asset.
- "Movie" is part of the backend routes, the admin URL matcher (`SecurityConfiguration.java:72-77`), the multipart
  gate (`MultipartRouteFilter.java:36-38`), the Nginx upload location (`deploy/nginx/nginx.conf:65-70`), the SPA routes
  (`AppRoutes.tsx:28-39`) and every `movieId` parameter of the contract.

Owner decisions this ADR implements:

1. **Model** (2026-11-25): an optional franchise, then titles (parts), then episodes, then video assets; a film is a
   title with one episode. Rename `movies` to `titles` first, in a change that alters no behaviour.
2. **Franchise hiding** (2026-11-25): a DRAFT or ARCHIVED franchise hides only its own page and strip; its PUBLISHED
   titles stay watchable.
3. **Continue Watching** (2026-11-25): one card per title, which becomes the next episode once the viewer finished one.
4. **Activation** (2026-11-25): READY means encoded; viewers get only the asset the admin activated. At activation the
   admin chooses "same cut" (resume, markers and subtitles kept) or "different cut" (resume from 0, history kept).
   Assets that exist at migration stay live. Activation ships with Admin Preview.
5. **Admin Preview** (2026-11-25): an exception for checking an encode and entering timed metadata before viewers see
   it, on a separate admin-only route with its own permission, an audit record and `no-store`. It writes no viewer
   progress, history or Continue Watching, and the viewer HLS routes are not loosened.
6. **Description** (2026-11-26): the admin's own description is optional and always wins; provider text is shown only
   when the admin wrote none.

## Decision

### D1 Hierarchy and ownership

- `franchises` (optional) → `titles` → `episodes` → `video_assets` → `encoding_jobs`.
- A title is one part, with `content_type` `MOVIE`, `TV_SEASON`, `OVA`, `ONA` or `SPECIAL` and an optional free
  `part_label` for the strip ("Season 2", "Spin-off"). A film is a `MOVIE` title with exactly one episode, at ordinal 1.
- A title belongs to at most one franchise, at a unique `franchise_order`. A part in two franchises (crossovers,
  alternative watch orders) is not modelled; editorial Collections (ADR-021, planned) group titles many-to-many
  without affecting visibility.
- The episode is the playable unit: upload, assets, the current or active asset, playback, HLS authorization, progress
  and history are per episode. Catalog metadata (genres, credits, poster, release year, maturity rating,
  description) stays on the title. An episode has `ordinal`, `display_label` ("12", "12.5", "SP1"), an optional
  `name` and `synopsis`, and a status.
- `title_relations` (sequel, prequel, side story) is not created until a consumer exists: AniList relation proposals
  (#246) or a related-titles shelf.
- Ownership, with no new module and no Maven cycle: catalog owns franchises, titles, episodes, the visibility check
  and the row locks; encoding owns assets, the single current/active-asset definition and the activation transaction,
  writing the episode's pointer through a narrow catalog port and running the carry steps that later modules
  register; progress owns progress, history and Continue Watching; playback owns playback info and HLS and Preview
  access.

### D2 Names and identity

- S1 renames `movies` to `titles`, `movie_genres` to `title_genres`, `movie_credits` to `title_credits`, and the
  `movie_id` columns of those tables, `ratings` and `watchlist_items` to `title_id`, with their constraints and
  indexes (`ux_movies_slug` to `ux_titles_slug`, and so on). `video_assets`, `playback_progress` and `watch_history`
  keep `movie_id` until S2 re-keys them, so no column is renamed twice.
- Titles keep their movie UUIDs, so old links and raw keys stay valid. Episodes get new random UUIDs: reusing the
  title's would let a title ID passed where an episode ID is expected work by coincidence for every film.
- An episode's title and an asset's episode never change after creation. `video_assets` has no title column; asset
  to episode to title is one join.
- Routes use UUIDs. Title slugs keep the ADR-009 rule; franchises get admin slugs under the same rule; episodes have
  none.
- `titles.description` becomes nullable, because the admin's own description is optional. ADR-014 (planned) owns the
  display precedence (the admin's text always wins; provider text only when the admin wrote none) and the metadata
  foundation slice applies the column change together with it. S1 keeps the column `NOT NULL`.

### D3 Visibility at three levels

- An episode is visible when `episodes.status = 'PUBLISHED' AND titles.status = 'PUBLISHED'`.
- A title is visible when `titles.status = 'PUBLISHED'`.
- A franchise is visible when `franchises.status = 'PUBLISHED'`. This gates only the franchise page, its strip, the
  franchise reference in title responses and the franchise name in search. A hidden franchise never hides its
  titles, and nothing about it leaks: title responses omit it, and its name no longer matches in search.
- The episode of a `MOVIE` title is always `PUBLISHED`, and its status cannot be edited while the title is `MOVIE`, so
  the title's status governs exactly as a movie's does today. Changing a title to `MOVIE` requires exactly one
  episode, at ordinal 1 and already `PUBLISHED`.
- Outside the admin exceptions below, every endpoint that takes a franchise, title or episode ID answers a hidden item
  with the same 404 as a missing one (`FRANCHISE_NOT_FOUND`, `TITLE_NOT_FOUND`, `EPISODE_NOT_FOUND`). Lists contain
  only visible items, for every role, and counts exclude hidden items before paging.
- Catalog owns one visibility check for all three levels (`MovieVisibility` becomes the content visibility, with the
  same two values); other modules reuse it and never re-implement the status rule.
- The admin exceptions are exactly `/api/v1/admin/**` (every status) and, from S5, `/hls/admin/**` (D9). Viewer title
  detail becomes published-only for every role, and the admin form reads `GET /api/v1/admin/titles/{titleId}`. This
  narrows ADR-009, where `GET`, `PUT` and `DELETE /api/v1/movies/{movieId}` were also admin exceptions.
- ADR-009 archive retention applies at each level: archiving keeps every child row, all media and every user record.
  Archiving a title hides its episodes without changing their rows; restoring it shows exactly its `PUBLISHED`
  episodes. A visible episode without an active asset is allowed, and clients hide Watch.

### D4 Order, membership and the multi-episode guard

- `episodes` has `UNIQUE (title_id, ordinal) DEFERRABLE INITIALLY IMMEDIATE`, so a reorder can defer the check inside
  its transaction. A reorder sends the complete ordered list of the title's episode IDs and gets 409
  `EPISODE_ORDER_CONFLICT` when the list differs from the stored set.
- `titles.franchise_id` and `titles.franchise_order` are both null or both set, with
  `UNIQUE (franchise_id, franchise_order) DEFERRABLE INITIALLY IMMEDIATE`; a franchise reorder works the same way and
  gets 409 `FRANCHISE_ORDER_CONFLICT`.
- Episodes are created by the admin, never from provider episode counts. A `MOVIE` title is created together with
  its episode in one transaction; other types start without episodes.
- Until S4 ships the viewer pages for parts and episodes, the server refuses to publish a title that is not `MOVIE`
  (409 `TITLE_PUBLISH_NOT_AVAILABLE`); its episodes can be prepared, uploaded and published in advance but stay
  invisible with their title. Viewers therefore never meet a series they cannot navigate, and before S4 the title page
  needs to open only a film's single episode. S4 removes the guard.
- An episode's successor is the episode with the next ordinal. When it is hidden or has no active asset, viewers are
  told only that the next episode is not available yet (nothing else about it leaks), and it is never skipped for a
  later one, so a viewer is never sent past an episode that is still being prepared. Playback info and
  Continue Watching use this one definition.

### D5 Locks

- Catalog writes lock top-down: franchise, then title, then episode. Moving a title between franchises locks both
  franchises in UUID order, then the title. Every write to an episode, including reorder, publish and a type change
  of its title, locks the title first, so ordinals, the `MOVIE` rule and the publish guard (D4) are checked under one
  lock. The existing catalog write retry keeps covering deadlocks.
- Upload, retry and activation lock only the episode row, `FOR NO KEY UPDATE`: today's movie lock, moved down one
  level. An episode's title never changes, and archive does not stop media writes (ADR-010 retention), so no parent
  lock is needed.
- From S5, a progress save locks the episode row `FOR SHARE` (D8). `FOR SHARE` conflicts with the
  `FOR NO KEY UPDATE` of activation, upload and episode edits, but not with other saves or with the `FOR KEY SHARE`
  that foreign-key checks take. `FOR KEY SHARE` would not conflict with activation, so the save cannot use it. Before
  S5 nothing but the worker changes the current asset, and the worker takes no episode lock, so the save keeps
  today's unlocked read.
- Each lock is the first statement that loads its row in the transaction, so a managed entity loaded earlier cannot
  hide a committed change (today's `MovieRowLocks` rule). No path locks a child before its parent, and no lock is held
  during a raw PUT, an HTTP call, a storage read or FFmpeg. The worker is unchanged: it locks only asset and job rows.

### D6 Media per episode (S2)

- Each upload creates a new asset of one episode. Newest means the greatest `(created_at, id)` of the episode, and
  `created_at` is assigned inside the asset and job transaction after the episode lock (ADR-010's rule, one level
  down).
- At most one `UPLOADED`, `QUEUED` or `PROCESSING` asset per episode: `ux_video_assets_episode_in_flight` replaces
  `ux_video_assets_movie_in_flight`, and 409 `VIDEO_UPLOAD_IN_PROGRESS` matches the new name. Two episodes of one
  title may upload at the same time; the single worker queues them.
- Retry (Sprint 9) accepts only the newest FAILED asset of its episode.
- The raw key is `{titleId}/{videoAssetId}.{ext}`. Existing keys already have that shape, because titles keep the
  movie UUIDs. The prefix serves human inventory only and never authorizes anything. HLS keys stay per asset.
- The upload route becomes `POST /api/v1/admin/episodes/{episodeId}/video`, with the same form, limits, codes and
  401/403 order. It moves at once in the controller, the multipart gate, the Nginx upload location, the SPA client,
  the contract and the smokes.
- **One definition of the current asset.** The playback lookup, the HLS check, the progress save and reads,
  Continue Watching, the catalog `videoStatus` lookup and the purge runbook all use one definition. From S2 to S5 it
  is today's rule per episode (the READY asset with the greatest `(created_at, id)`); S5 replaces it with the active
  asset (D7) in that one place. It may be one SQL fragment or a view; a test or a check proves that no reader keeps a
  copy.

### D7 Activation (S5)

**Semantics.** READY means encoded and validated. Viewers get only the episode's **active** asset, which the admin
chose. A newly READY asset, first upload or replacement, is a **candidate** until the admin activates it. Each asset
that is current when S5 migrates becomes active, so nothing that plays today stops playing.

**State.**

- `episodes.active_video_asset_id uuid NULL`, with the composite foreign key
  `(id, active_video_asset_id) REFERENCES video_assets (episode_id, id)`, so the active asset always belongs to its
  episode. This needs a unique constraint on `video_assets (episode_id, id)`.
- `episodes.activation_generation bigint NOT NULL DEFAULT 0`, incremented by every activation, including a return to
  an earlier asset (A, then B, then A again). Clients only compare it for equality.
- `video_assets.timeline_id uuid NULL` says which cut a stored position belongs to. It is null until the asset is
  first activated, and every activation sets it: `SAME` gives the asset the active asset's timeline, `NEW` a new
  random one, also when an earlier asset is activated again. Two assets share a timeline only through `SAME`, so a
  `NEW` activation always restarts every stored position of the episode. Timed data is carried by copying rows
  (below), never keyed by timeline, so a changed timeline orphans nothing.
- `video_assets.retired_at timestamptz NULL` marks an asset whose HLS objects may be gone. A retired asset can never be
  activated or previewed. The purge procedure sets it before deleting any object, and the S5 migration sets it on
  older READY rows (see Seeding), so no path can make purged media live again.
- The worker writes none of these, so READY alone changes nothing a viewer sees. ADR-010 rejected a current-asset
  pointer for three reasons: a worker catalog write, a foreign-key cycle and a stale JPA pointer. Admin activation
  removes the first. The cycle between `episodes` and `video_assets` is harmless: the pointer is nullable, so inserts
  order naturally, and neither row is ever hard-deleted. The pointer is mapped as a plain UUID that only the
  activation transaction writes. Readers take the pointer and the generation under the episode lock or in the same
  statement as the asset the pointer names, so a stale entity cannot decide anything.

**The transaction.** `POST /api/v1/admin/video-assets/{videoAssetId}/activation` with
`{"timeline": "SAME" | "NEW", "expectedActivationGeneration": n}`:

1. Read the asset's episode ID with a scalar query, before any entity is loaded in the transaction. A missing asset is
   404 `VIDEO_ASSET_NOT_FOUND`.
2. Lock the episode `FOR NO KEY UPDATE`. When `activation_generation` differs from `expectedActivationGeneration`,
   answer 409 `ACTIVATION_CONFLICT`: another activation won, or the dialog is stale.
3. The asset must be READY, not active and not retired; otherwise 409 `VIDEO_ASSET_NOT_ACTIVATABLE`.
4. Timeline. `SAME` requires an active asset and gives the asset that asset's `timeline_id`; without an active asset it
   is 409 `VIDEO_ASSET_NOT_ACTIVATABLE`. `NEW` gives the asset a new random one. The same choice applies when an
   earlier asset is activated again (a return to a known good encode): the admin declares its relation to what viewers
   watch now, so A, then B as `NEW`, then A as `NEW` restarts every position, exactly as the owner's "different cut"
   rule says, while A as `SAME` keeps the positions saved on B.
5. Apply the carry rules below in the same transaction, for both choices: `SAME` keeps the asset's own sets or copies
   the active ones, and `NEW` removes the carried rows an earlier activation left on the asset.
6. Set `active_video_asset_id`, increment `activation_generation` and commit. No storage I/O, HTTP call or media work
   runs inside the transaction.
7. Answer 200 `{episodeId, activeVideoAssetId, timelineId, activationGeneration}` and log one INFO event with the
   admin's user ID, the episode, the previous and new asset, the `SAME` or `NEW` choice, the generation and the
   request ID.

Activation works for every episode and title status, so the admin can prepare a DRAFT episode and publish it
afterwards. A double click gives one 200 and one 409 `ACTIVATION_CONFLICT`. After an unknown outcome (a network
error, a timeout or a 5xx), the admin page reads the preview info again instead of resending blindly; a resend with the
same expected generation can never activate twice.

**Carry on SAME.** Timed data the admin attaches to an asset (sidecar subtitle tracks, ADR-019 markers, both planned)
belongs to the cut, not to one encode. Each row of such a set is either the asset's own (entered or confirmed by the
admin on it) or carried. The activated asset, whether a candidate or an earlier asset returning, is handled per kind
of set, deterministically and idempotently:

- on `SAME`, if the asset has its own confirmed set of that kind, that set stays and its carried rows of that kind
  are removed; otherwise its carried rows are replaced by a copy of the active asset's set as viewers see it (own or
  carried), which may be empty;
- on `NEW`, its carried rows are removed and its own rows stay.

Carried time ranges are validated against the activated asset's duration; a range that does not fit blocks the
activation with 409 `ACTIVATION_CARRY_INVALID` and field errors. The request echoes the revision of each set the admin
reviewed, and a change since then is 409 `ACTIVATION_CONFLICT`. Data that belongs to one encode (audio
renditions, seek thumbnails, subtitles the worker extracted from the source) is never carried. This ADR owns the hook:
each later ADR that adds such a set registers its carry step and its revision field. S5 carries the sets that exist
when it lands.

**Classes.** Per episode:

- active: the asset the pointer names;
- candidate: READY, never activated (`timeline_id IS NULL`) and not retired, whatever its age;
- superseded: READY and neither active nor candidate (replaced after being active, or retired), or FAILED and not the
  newest asset.

Purge selects only superseded assets and never an active or candidate one; the runbook query switches to these classes
in S5. With writers stopped (which also stops activation), the procedure sets `retired_at` on each reviewed asset and
commits before it deletes any object. A candidate the admin never activates stays retained until an explicit admin
discard action exists (with the Sprint 9 asset list or later). Releasing a raw original (ADR-016, planned) requires
activation.

**Viewer availability.** An episode's viewer `videoStatus` is READY only when it has an active asset. Otherwise it is
the newest asset's status, except that a READY candidate is reported as `PROCESSING`: for a viewer, an encode that
waits for the admin is still being prepared. The admin projection shows `active` and `candidate` explicitly.

**Seeding (S5 migration).** Each episode's current asset under today's rule becomes active, with a new `timeline_id`
and generation 1. Every other READY asset is retired: it was live once under ADR-010 D14, but the manual purge may
already have deleted its objects, and nothing in the database records that. No READY row that exists at the migration
becomes a candidate. Episodes without a READY asset keep a null pointer and generation 0.

### D8 Progress, history and Continue Watching

- Progress and history are per episode: `playback_progress` has the primary key `(user_id, episode_id)`, and
  `watch_history` is unique on `(user_id, episode_id)` and keeps its row IDs. Ratings and the watchlist stay per
  title (D10).
- Until S5, ADR-011 D9-D14 apply per episode unchanged: the save names the current asset (409
  `VIDEO_ASSET_NOT_CURRENT` otherwise), positions are clamped and `finished` is derived against that asset, and a
  replacement carries positions with a clamp.
- **From S5, a position belongs to a timeline.** `playback_progress.timeline_id` records the active asset's timeline
  at each accepted save. Reads compare it with the active asset's timeline: when equal, ADR-011 D11 normalizes as
  today; when different, the position and `resumeSeconds` are 0, while `finished` and history are kept (a different
  cut). The S5 migration sets every existing row to the timeline of its episode's seeded active asset, which is what
  ADR-011 D14 would do one last time. Progress stores no asset ID: the timeline is what every reader compares, and a
  stored asset ID of an older encode would need a shared timeline that claims two encodes are one cut.
- **A save and an activation never interleave.** A save locks the episode `FOR SHARE` first (D5), then checks
  visibility (404), the active asset (409 `VIDEO_NOT_READY` without one), that `videoAssetId` names it and that
  `activationGeneration` equals the episode's (409 `VIDEO_ASSET_NOT_CURRENT` otherwise). It then upserts with the
  active timeline and writes history as ADR-011 D9-D12 specify, and commits. An activation waits for running saves,
  and later saves wait for the activation, so no save checked against one activation is stored under another, and a
  late save from an earlier activation of the same asset (A, B, then A again) is refused. Comparing the generation
  without the lock would still race: a save that read the old state can commit after the activation.
- `activationGeneration` is required in `ProgressRequest` from S5. A tab opened before the S5 release gets 400
  `VALIDATION_ERROR` on its saves until it reloads; S5 is one coordinated release, and no other client exists.
- **Continue Watching per title** (replaces the list of ADR-011 D11). For each title, the anchor is the caller's most
  recent progress row on a visible episode, chosen before any filter on `finished` or position, so an episode that
  lost its media never brings back an older one.
  - The card is `RESUME` for the anchor's episode when the anchor is not finished and is resumable: on the active
    timeline, with a normalized position above 0 and below the duration. A finished anchor is never `RESUME`, also
    when it was finished at 90% before the end, so a finished film leaves the list as it does today.
  - The card is `NEXT_EPISODE` when the anchor is finished. It names the anchor's successor (D4: the episode with the
    next ordinal) and shows that episode's own normalized progress, if any.
  - There is no card when the anchor is neither finished nor resumable, or when the successor does not exist, is
    hidden, has no active asset (it is never skipped for a later one) or is already finished.
  - Membership, one card per title and the order (anchor `last_played_at` descending, then title ID) apply before the
    limit of 50. No progress or history row is invented. Films behave exactly as today, and the response stays an
    array.

### D9 Admin Preview and the activation enablement set (S5)

Activation ships in one release with everything that makes it safe to use. The Preview's own permission is
`ROLE_ADMIN` checked against the database on every request; no new role is added.

- **Preview info.** `GET /api/v1/admin/video-assets/{videoAssetId}/preview` answers, for any READY asset that is not
  retired (active, candidate, or replaced but still restorable), whatever the episode and title status,
  `PreviewInfo {videoAssetId, episodeId, titleId, durationSeconds, hlsManifestUrl, active, candidate, timelineId,
  activeVideoAssetId, activeTimelineId, activationGeneration}`; a missing, non-READY or retired asset is 404
  `VIDEO_ASSET_NOT_FOUND`. Each call logs one INFO event (admin user ID, asset, request ID), which is the audit
  record. Later ADRs add their fields (tracks, markers, seek previews).
- **Preview HLS.** `/hls/admin/video-assets/{videoAssetId}/master.m3u8` and `.../segments/{segmentName}` mirror the
  viewer routes for the same assets as Preview info: the same stored-key and segment-name checks, whole-object
  responses and errors
  (404 `VIDEO_ASSET_NOT_FOUND`, 503 `HLS_STORAGE_UNAVAILABLE`). `/hls/admin/**` joins `ADMIN_ENDPOINTS`
  (`SecurityConfiguration.java:72-77`), so every request reads the session and the database role directly (ADR-012):
  a demoted or signed-out admin is refused with 403 or 401 on the next request. `HlsRouteFilter` already sets
  `Cache-Control: no-store` on every `/hls/*` response before security runs, denials included; its denial log learns
  the admin path and also logs 403. Nginx's `/hls/` location needs no change. The viewer routes do not change and
  still answer 404 for candidates and hidden content.
- **Minimal Preview player.** The admin page reuses today's player with an explicit Preview policy: no save timer, no
  pause, seek, end, visibility or `pagehide` saves, no unmount save, no Continue Watching refresh and no current-asset
  handler. It never calls the viewer playback API and never switches to another asset; a 404 says that this encode
  can no longer be previewed. The authenticated loader's URL check, today the `/hls/video-assets/` prefix
  (`hlsAuthentication.ts:261-265`), becomes the exact prefix of the asset this run plays, viewer or admin, and the
  playback-info decoder accepts the admin manifest path only for Preview.
- **Entry point.** The admin reaches Preview and activation from the per-episode asset list (#168, the ADR-011 D17
  projection with `active`, `candidate` and `retired`), which links each READY asset that is not retired to its
  Preview; the episode's admin page shows when a candidate is waiting. S5 does not ship before that list exists, so a
  READY first upload can always be found and activated later, not only from the upload response.
- **Activation dialog.** It states `SAME` or `NEW`, what carries over and what viewers lose, and sends the generation
  it showed.
- **Viewer reload rule** (the client half of the ADR-011 D14 replacement). An HLS 404 or a progress 409 starts one
  shared playback-info refetch (`playbackRun.ts:211-222`). The answer is applied once, from the run's actual state
  when it arrives, whichever trigger started it:
  - a different asset, or the same asset with a different `timelineId`: a new run starts at the live position when
    `timelineId` is unchanged and the position lies inside the new duration, and otherwise at the refetched
    `resumeSeconds`;
  - the same asset and timeline with a newer generation (the asset was activated again as `SAME`): if hls.js is still
    running, the run adopts the generation and keeps saving under it; if an HLS 404 has already destroyed hls.js
    (`playbackRun.ts:186-199,255-267`), a new run starts at the live position. Adopting a generation never cancels a
    restart that a destroyed run needs.

  Every new run resets the run's memory so no save of the old cut can be sent, and the saver stops by asset and
  generation instead of by asset alone (`progressSaver.ts:78-80`). Today a same-asset answer leaves the player stopped
  or showing Retry, and a new asset keeps the old position (`playbackRun.ts:228-239,403-413`), which a `NEW`
  activation must not do.

ADR-019 (planned) adds the Marker Editor and the full Preview tools to this route; it does not redefine it.

### D10 Library and search levels

- Ratings and the watchlist are per title; progress and history per episode. Recommendations count episode signals
  once per title (ADR-015, planned).
- Search indexes titles: one card per visible title, with its type and episode count; a visible franchise's name is a
  search name of each of its parts. The search tables, normalizer and tiers belong to ADR-015 (planned), which reuses
  the D3 predicate and decides the fate of the unused `search_vector` column.

### D12 Provider mapping principles

ADR-014 (planned) owns the adapters, external-ID tables, provenance and refresh. This ADR fixes what they map onto:

- Mappings are explicit and chosen or confirmed by the admin. Nothing is inferred from names, and episodes are never
  created from provider counts.
- External IDs are scoped per level (franchise, title, episode) and created against the renamed tables.
- TMDB: a movie maps to a `MOVIE` title. A TV show is context shared by several titles, never one title or a
  franchise. Each season the admin picks maps to one title (`TV_SEASON`; season 0 usually `SPECIAL`), and each TMDB
  episode to one episode the admin created. A TMDB collection may suggest a franchise, never create one.
- AniList: one Media maps to one title, and its format suggests the type (`TV` and `TV_SHORT` to `TV_SEASON`,
  `MOVIE`, `OVA`, `ONA`, `SPECIAL`; `MUSIC` is not imported). Relations (`SEQUEL`, `PREQUEL`, `SIDE_STORY`,
  `SPIN_OFF`, `ALTERNATIVE` and the rest) only propose franchise membership and order, which the admin confirms.
  AniList has no episode objects, so episodes stay admin-entered.

### D13 Migration, cutover and rollback

Every slice adds a Flyway migration after V6 and never edits a committed one. Each migration runs in one PostgreSQL
transaction, with preflight checks that stop for an explicit data decision instead of choosing a winner (V5's
pattern). The pull request that adds a migration regenerates the schema snapshot. Each is rehearsed by a
populated-upgrade smoke on PostgreSQL 16 with ICU `vi` (precedent: `deploy/tests/video-asset-migration-smoke.sh`),
including the runtime roles' grants (`deploy/flyway/afterMigrate.sql`), a fresh install and a forced failure that
rolls back. No object moves in storage, nothing is re-encoded and the queue does not change: messages carry only IDs.

- **S1, rename.** Catalog-only DDL: table, column, constraint and index renames; foreign keys follow their tables. The
  code changes entity mappings, native SQL, constraint-name constants, fixtures (worker tests included), the snapshot
  and the purge SQL. The unchanged backend, frontend, Newman and worker suites are the oracle.
- **S2, episodes in one deployable cutover.** One migration:
  - `titles.content_type` (backfilled `MOVIE`, no default afterwards, `CHECK` on the five values) and `part_label`;
  - `episodes`, with one `PUBLISHED` episode at ordinal 1 and a new UUID per title;
  - `video_assets.episode_id` (backfilled), `ux_video_assets_episode_in_flight`, a READY-order index on
    `(episode_id, created_at DESC, id DESC) WHERE status = 'READY'`, and `movie_id` dropped with its two indexes;
  - `playback_progress` and `watch_history` re-keyed in place on `episode_id`, `NOT NULL` after the backfill, with
    `watch_history` row IDs kept and the progress index on `(user_id, last_played_at DESC, episode_id DESC)`;
  - new foreign keys from catalog to media and to user data are `ON DELETE RESTRICT`; user foreign keys stay `CASCADE`.

  The backend, the Nginx upload location, the multipart gate, the admin matcher and the SPA switch in the same
  release. If the backend merges before the SPA, an optional merge bridge keeps both route families working through
  Nginx until the SPA switch lands; both states are tested, the bridge never enters the contract, and it is gone when
  S2 closes. An SPA tab opened before the S2 release gets no upload bridge: every upload click of that build first
  reads `GET /api/v1/movies/{movieId}` (`useVideoUpload.ts:87-101`), which S2 removes, and any failure there ends the
  attempt as "not found" or "the file was not sent" before a byte of the body is sent. The deployment drains uploads
  that are already sending (below), and reloading the tab loads the new SPA. One residual case is accepted: a tab
  whose script is frozen between a successful check and its `POST` for the whole deployment would send the body to
  the removed path and end in the edge's 413 or a lost connection, reported as not accepted or unknown. Nothing is
  stored in that case, a reload and a new upload fix it, and it needs a pause of minutes inside a window of
  milliseconds, so it does not justify a second upload route. A test runs the previous build's upload button against
  the deployed S2 configuration and confirms that no request body reaches the edge.
- **S3, franchises.** `franchises` and the two title columns; no data change.
- **S5, activation.** `episodes.active_video_asset_id` and `activation_generation`, `video_assets.timeline_id` and
  `retired_at`, the `(episode_id, id)` unique constraint and `playback_progress.timeline_id NOT NULL`, seeded as D7 and
  D8 describe. A preflight stops when a progress row's episode has no READY asset (an accepted save always required
  one).
- **Deployment of every migration slice (S1, S2, S3, S5).** A previous backend cannot run against renamed tables (S1),
  re-keyed tables (S2) or a new `NOT NULL` column (S5), so each release runs the same fenced sequence:
  1. stop new uploads at the edge and wait until no upload request is in progress, so no accepted body is cut;
  2. stop the edge and the backend, so no job is published or relayed; the worker keeps consuming what the broker
     already holds;
  3. drain the worker: wait until the encoding queue is empty and no job is `PROCESSING`, then stop it. Checking for
     no `PROCESSING` job while messages remain is not enough, because the worker may claim the next one before it
     stops. If the operator cannot wait for the queue, stopping the worker may interrupt one encode, which then fails
     as `WORKER_INTERRUPTED` at the next start and needs a retry or a new upload. Unpublished QUEUED jobs stay in
     PostgreSQL for the relay;
  4. take a `pg_dump` and restore it once into a disposable container;
  5. run the migration and its checks (schema snapshot, row counts, the preflights) with every writer still stopped;
  6. decide there: if anything failed, restore the dump and start the previous images; otherwise start the new
     backend and worker, then the edge.
- **Rollback.** Restoring the dump is possible only at step 6, before any backend or worker of the new release has
  run: from then on PostgreSQL, the broker and the object store move together, and the only way back is forward.
  Never collapse episodes back into movies and never delete media.
- **URL compatibility (S2).** SPA routes `/movies` go to `/titles` and `/movies/:id` to `/titles/:id` (same UUID).
  `/movies/:id/watch` goes, after an authorized fetch of the title, to `/watch/:episodeId` for a `MOVIE` title and to
  `/titles/:id` otherwise, never picking an episode silently. Admin `/admin/movies/...` routes go to
  `/admin/titles/...`. All stay under the existing guards and use `replace` navigation. There is no JSON alias (D11).
- **Interim states.** After S1 nothing changes for users. After S2 every title is a `MOVIE` with one episode, served on
  the new routes, and the admin can create only `MOVIE` titles. After S3 the admin can build and prepare series, but
  only `MOVIE` titles can be published until S4. ADR-010 D14 and ADR-011 D14 apply per episode until S5.

## Options Considered

| Topic | Selected | Alternatives and reason not selected |
|---|---|---|
| Hierarchy | Optional franchise, title, episode, asset | Separate movie and series trees: two playable identities, so playback, HLS, progress, upload and search all branch on type. A generic recursive node: cycles and recursive visibility on every HLS request. A series layer between franchise and season: one more gate with no demonstrated need. A franchise as a many-to-many collection: no single visibility gate; kept as Collections. |
| Table name | Rename to `titles` in a slice that changes no behaviour | Keeping `movies` as the title table: every later table (metadata, aliases, search names) would reference a misnamed parent, and a larger rename would follow. |
| Moving media and progress | Re-key in place in one transaction | New tables with read-only copies: no recovery path beyond a verified dump once new writes exist, and `afterMigrate.sql` grants DML on every table, so a read-only copy needs an exception. |
| Episode UUID of a film | New UUID | Reusing the movie UUID lets title-for-episode mistakes pass every film test. |
| Title column on assets | None | A composite foreign key adds an index and a consistency rule that no reader needs. |
| Franchise visibility | Gates only itself | A strict gate would let an editorial regrouping revoke watchable content and direct links. |
| What goes live | Admin activation, with `SAME` or `NEW` chosen then | The greatest READY asset (today): an unchecked encode reaches viewers. A same-or-different tag at upload: chosen before anyone saw the encode. A duration match alone: cannot tell two cuts of one length apart. |
| Activation state | Pointer and generation on the episode, timeline per asset | `activated_at` or an activation sequence on assets, greatest wins: no foreign-key cycle, but every reader, one per HLS segment, needs an anti-join again, and the generation still lives on the episode. Forbidding re-activation: loses the return to a known good encode. |
| Save against activation | Episode row lock `FOR SHARE` in the save | A generation compare without a lock races with a commit between the read and the upsert; `FOR KEY SHARE` does not conflict with activation; an advisory lock adds a second lock namespace for the same row. |
| What a progress row records | Its timeline | The asset ID: rows saved on an older encode before S5 would need a shared timeline that claims two encodes are one cut, or a rewrite of the stored asset. |
| Old URLs | SPA redirects only | Long-lived `/movies` JSON aliases: a second contract to test, with no external client. |
| Continue Watching | One card per title, `RESUME` or `NEXT_EPISODE` | One card per episode fills the list with one series; dropping a title when its episode is finished removes it exactly when the next episode matters. |
| Purged media | `retired_at`, set before any object is deleted; older READY rows retired at S5 | Checking object existence at activation: storage I/O inside a decision that must be transactional, and a partly purged prefix can still pass. Letting purged rows be activated: replaces working playback with 404s. |

### Migration cost of the hierarchy options

| Option | Existing films and their IDs | Assets, progress, history, ratings, watchlist | Links and bookmarks | Cutover and rollback |
|---|---|---|---|---|
| Selected: optional franchise, title, episode | each movie becomes a `MOVIE` title with the same UUID plus one new episode | re-keyed in place in one transaction (S2); ratings and watchlist only renamed (S1) | old SPA routes redirect; raw keys unchanged | one fenced release per slice; dump restore before the first new write |
| Separate movie and series trees | films untouched | series need a parallel set of asset, progress and history tables, or a type column on every reference | film links unchanged; new series routes | small first step, but every later feature (search, library, activation) is built twice |
| Generic recursive node | every movie becomes a node; parents added later | every reference moves to node IDs; visibility needs a recursive query in every check | redirects needed for every level | the same cutover size as the selected option, with a harder visibility rule to verify |
| Franchise as a many-to-many collection only | as selected, but titles get no single parent | as selected | as selected | as selected; the cost moves to every visibility check, which has no single parent to gate on |
| Keep the `movies` table name | no rename | as selected | as selected | one migration fewer now; a second, larger rename later, after metadata and search tables reference `movies` |

## Consequences

- Sprint 7 search, the Sprint 8 library and every later design key on titles, episodes and the active asset.
- S2 changes the backend, Nginx, the multipart gate, the admin matcher and the SPA in one release, and its deployment
  stops writers for a short window.
- From S5 a new encode never reaches viewers by itself: the admin activates every first upload and every replacement.
  Until then, ADR-010 D14 and ADR-011 D14 still apply per episode.
- From S5 a progress save takes a shared lock on its episode row. It writes the row's lock information and waits for
  a running activation, upload commit or episode edit, each a short transaction; the k6 measurement before deployment
  covers it.
- After a `NEW` activation, viewers restart that episode from 0; their history and `finished` stay.
- `episodes` and `video_assets` reference each other; a hard delete of either would need an ordered procedure, and the
  product has none.
- A title of a series type is `UNAVAILABLE` until it has a visible episode with a playable asset.
- Documents: ADR-009, ADR-010 and ADR-011 gain addenda; SECURITY, ERD, API-CONTRACT and SEQUENCE-DIAGRAMS gain
  planned sections. INFRASTRUCTURE (upload transport), the deployment runbook (purge query, upgrade steps),
  OBSERVABILITY (activation and Preview log events) and the contract paths change in S2 and S5 together with their
  code. The requirement documents (BACKLOG, TRACEABILITY, USERSTORIES) are updated by a separate decision-record pull
  request.
- This document proves only the design. S1-S5 each need their own migration, race and browser evidence; #125-style
  browser evidence alone establishes upload, encoding and playback on the new routes.
