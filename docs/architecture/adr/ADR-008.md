# ADR-008: Case-insensitive email identity

Status: Accepted; user approved during the Sprint 2 independent closeout on 2026-09-17.

## Context

Exact-string lookup and uniqueness allowed `User@example.com` and `user@example.com` to become separate login identities. The previous frozen contracts did not specify case handling. This is an application identity decision, not a claim that all mail providers treat local parts identically.

## Decision

Use the database's `lower(email)` expression, with the same database collation, for registration duplicate lookup, login lookup, and a new unique index `ux_users_email_identity`. Preserve the submitted email spelling in the existing column and profile response. Do not strip dots, plus tags, whitespace, or apply provider-specific aliases; existing email validation still applies. No Java-side Unicode case folding is used, avoiding disagreement with PostgreSQL.

Retain the existing `ux_users_email` constraint. Add Flyway V4; never edit committed migrations. Lock writes while checking for existing case collisions and creating the expression index. If a collision exists, abort atomically without logging the conflicting addresses or changing either account. Account recovery/merging requires a separate authorized decision. Back up the database and resolve collisions before retrying deployment; do not bypass the index.

## Consequences

- Case variants log into the same account and registration returns 409, including concurrent requests.
- PostgreSQL integration tests must verify enforcement; Hibernate-generated H2 schemas do not represent the expression index.
- A database collation change requires rechecking identity collisions and rebuilding the affected index as a separately reviewed migration.
- API paths, payload shapes, status codes, user IDs, roles, and password/token contracts remain unchanged.
