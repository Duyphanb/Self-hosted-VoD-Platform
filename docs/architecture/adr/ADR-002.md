# ADR-002: Java 21, Spring Boot 4.x, Maven Multi-Module

Status: Frozen for MVP implementation

## Status

Accepted. Amended on 2026-10-18 to move from Spring Boot 3.x to Spring Boot 4.x; see [Amendment (2026-10-18)](#amendment-2026-10-18).

## Context

The backend and worker need a maintainable Java foundation that supports REST APIs, validation, security, persistence, testing, and operational health checks.

## Decision

Use Java 21, Spring Boot 4.x, and Maven multi-module structure for backend and worker development.

## Options Considered

| Option | Pros | Cons |
|---|---|---|
| Java 21 + Spring Boot | Modern LTS Java, strong ecosystem, good portfolio signal | Requires disciplined module boundaries |
| Node.js backend | Same language as frontend | Weaker alignment with Java backend portfolio goal |
| Separate repositories | Cleaner isolation | More overhead for a solo portfolio project |

## Consequences

- Backend and worker can share Java conventions and test tooling.
- Spring Security, Spring Data JPA, Validation, Actuator, and Springdoc fit the MVP.
- Maven modules must stay simple and not become a premature enterprise framework.

## Amendment (2026-10-18)

The original decision named Spring Boot 3.x. This amendment changes it to Spring Boot 4.x under [Issue #50](https://github.com/Duyphanb/Self-hosted-VoD-Platform/issues/50). Java 21 and the Maven multi-module structure are unchanged.

### Reason

- Spring Boot 3.5.16 was the last open-source Spring Boot 3 release, so the Boot 3 line no longer receives open-source fixes.
- CVE-2026-47884 and CVE-2026-47890 in `spring-webmvc` are fixed in open source only in Spring Framework 7.0.9, which requires Spring Boot 4. Neither has an open-source fix on the Spring Framework 6.2 line used by Spring Boot 3.5.
- Of the options recorded in Issue #50 (Spring Enterprise Boot 3 artifacts, a time-bounded Boot 3.5.16 exception, or a Spring Boot 4 migration), this amendment selects the Spring Boot 4 migration. No Boot 3.5.16 exception remains.

### Consequences

- The platform moves to Spring Framework 7, Spring Security 7, Hibernate ORM 7, and Tomcat 11.
- Jackson 3 replaces Jackson 2: `ObjectMapper`, `JsonNode`, and the other core and databind types live under `tools.jackson`. Jackson annotations stay under `com.fasterxml.jackson.annotation`.
- Spring Boot uses modular starters: `spring-boot-starter-webmvc` replaces `spring-boot-starter-web`, `spring-boot-starter-security-oauth2-resource-server` replaces `spring-boot-starter-oauth2-resource-server`, and tests use the matching test starters, such as `spring-boot-starter-webmvc-test` and `spring-boot-starter-data-jpa-test`.
- Test slices and test auto-configuration moved to per-technology packages, for example `org.springframework.boot.data.jpa.test.autoconfigure.DataJpaTest` and `org.springframework.boot.webmvc.test.autoconfigure.AutoConfigureMockMvc`. `RestTestClient` replaces `TestRestTemplate`, and `@MockitoBean` replaces the removed `@MockBean`.
- Spring Security 7 removed `AntPathRequestMatcher`; request matchers use `PathPatternRequestMatcher`.
- When Springdoc is added, it must use a release line that supports Spring Boot 4.
- A future major platform upgrade needs another amendment and a complete migration in one change, verified across backend, worker, persistence, containers, and the auth lifecycle. A parent-only major version bump is not merged.

### Support model

- **Platform:** open-source Spring Boot 4.x through `spring-boot-starter-parent`. Follow each new Spring Boot 4.x minor release and apply its patch releases through routine dependency updates.
- **Maintainer:** the repository owner (`Duyphanb`) is accountable for platform updates.
- **Monitoring:** the weekly scheduled dependency audit, which also runs on every pull request and push to `main`, as described in [DEPENDENCY-SECURITY.md](../../testing/DEPENDENCY-SECURITY.md).
- **Response:** fix HIGH and CRITICAL findings in the current sprint. Override a version managed by the Spring Boot parent only for a third-party library, through the parent's version property, with a documented reason and removal condition; never override individual Spring artifacts.

## Amendment (2026-10-18): shared backend module

Approved by the repository owner under [Issue #113](https://github.com/Duyphanb/Self-hosted-VoD-Platform/issues/113).

- **Reason:** `common` already served as the Spring Boot assembly module, because it holds the entry point and depends on `auth` and `user`. Feature modules therefore could not depend on it without a cycle. The API error model and the only `Clock` bean lived in `auth`, so every new feature module, starting with `catalog`, would have had to depend on `auth` and its OAuth2 and persistence internals just to return an error or read the time.
- **Decision:** a small `shared` module holds the API error model (`ApiError`, `ApiFieldError`, `ApiException`), the generic exception handling, the single app-wide `Clock` bean (`appClock`), and reusable validation constraints. It has no JPA or security dependencies and depends on no feature module. `common` is the assembly module. See the module list in [SYSTEM-ARCHITECTURE.md](../SYSTEM-ARCHITECTURE.md).
- **Consequences:** feature modules depend on `shared`, never on each other only for errors or time. Each feature module keeps its own exception types and advice, and no exception type is handled by two advices. Modules must not define another `Clock` bean; a full-context test enforces this.
