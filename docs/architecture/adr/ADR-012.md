# ADR-012: Browser session — HttpOnly refresh cookie, in-memory access token and bounded revocation

Status: Frozen decision (merged in #228). Issue 6.9 shipped in #237. Issue 6.10 is tracked in #231.

## Context

- [ADR-007](ADR-007.md) delivers the refresh token in JSON bodies and deferred an HttpOnly cookie as "post-MVP hardening". The frontend keeps both the access token and the refresh token in `window.localStorage` (`frontend/src/features/auth/AuthContext.tsx:70`, `authStorage.ts`). Any script running in the origin can read a refresh token that lives for 7 days and slides on every rotation (`RefreshTokenService` issues a new expiry on each rotation).
- The access token lives 60 minutes (`application.yml:54`, `.env.example`), and the JWT validator accepts the Spring Security default clock skew of 60 seconds (`AuthTokenConfiguration`, `JwtValidators.createDefault()`). Logout revokes only the refresh token (`LogoutService`); the JWT converter trusts the claims and never reads the account (`AccessTokenAuthenticationConverter`), and it turns every runtime exception into an invalid-token 401. A logged-out, disabled or demoted user keeps every access right until the access token expires.
- A replayed (already rotated) refresh token is rejected, but its successor chain stays valid; there is no session or family, no absolute session lifetime, no per-user session cap and no pruning of `refresh_tokens` (#72, 2026-10-06 comment).
- Today every refresh failure, including a network error or a 5xx, ends the session in the SPA (`client.ts` calls `onAuthenticationFailure` on any refresh exception). ADR-011 D2 changes that; this ADR moves the change into Issue 6.9 because the cookie bootstrap needs it (D7).
- Issue 6.6 (#223) is about to build the hls.js player on the shared `ApiClient` recovery (ADR-011 D2). Changing token storage after it would rewrite the same code twice, and the browser end-to-end test (#125) should exercise the final session model.
- The owner's principle (2026-11-18): the MVP label is not a reason to keep a weaker design when a better one has a demonstrable benefit at a reasonable cost.

This ADR keeps bearer-header authentication for every API and HLS request (ADR-011 D1-D3), the BCrypt password rules, RBAC with `ROLE_USER`/`ROLE_ADMIN`, and the single backend instance of the single-VPS deployment.

## Decision

The decisions ship in two steps: **Issue 6.9** (D1-D3, D7 and the 6.9 part of D9) changes token transport and storage; **Issue 6.10** (D4-D6, D8 and the 6.10 part of D9) adds sessions and bounded revocation. D9 defines the state between them.

### Token placement and transport (D1-D3)

**Refresh token in an HttpOnly cookie; access token only in memory (D1).**

- The refresh token never appears in a response body, a request body, `localStorage`, `sessionStorage` or IndexedDB. The server sets it as one cookie:
  - name `vod_refresh`;
  - `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth`; no `Domain` attribute (host-only);
  - `Max-Age` equal to the remaining lifetime of the refresh token (after Issue 6.10: of the session, D4), so the browser drops it when it can no longer work.
- `Secure` is on by default. It may be turned off only by explicit configuration whose allowed origins are all loopback origins (local HTTP development); startup fails otherwise, and the production preflight (#138) rejects it. Issue 6.9 verifies in Chrome and Firefox that the local `http://localhost` stack works with the chosen setting.
- The `/api/v1/auth` path keeps the cookie off every other request, including `/hls/*`; no cookie ever authenticates an API resource or an HLS request.
- The access token is held in JavaScript memory only. A page load has no access token and obtains one through the refresh endpoint (D7).

**Endpoints (D2).** Breaking contract changes, shipped together with the frontend in Issue 6.9:

| Operation | Request | Success | Failures |
|---|---|---|---|
| `POST /api/v1/auth/login` | `LoginRequest` (unchanged); the browser may also send an existing `vod_refresh` | 200 `AuthResponse` (`user`, `accessToken`, `expiresInSeconds`; no `refreshToken`) and `Set-Cookie: vod_refresh=…`. A valid refresh token presented with the request is revoked first (after Issue 6.10: its whole session), because this browser now belongs to the new sign-in | 400, 401 as today; 403 `ORIGIN_NOT_ALLOWED` (D3) |
| `POST /api/v1/auth/register` | `RegisterRequest` (unchanged) | 201 `UserProfile` (unchanged; registration does not sign in) | 400, 409 as today; 403 `ORIGIN_NOT_ALLOWED` |
| `POST /api/v1/auth/refresh` | no body; the `vod_refresh` cookie | 200 `AuthResponse` and a rotated `Set-Cookie` | 401 `UNAUTHORIZED` for a missing, unknown, expired, revoked, over-long (more than 128 characters), duplicated (D3) or replayed cookie, which also clears the cookie (`Max-Age=0`); 403 `ORIGIN_NOT_ALLOWED`; a failure to read the token state is 503, never 401 (D6) |
| `POST /api/v1/auth/logout` | no body; the cookie when present | 204, idempotent: revokes the presented refresh token (after Issue 6.10: its session) when there is one and always clears the cookie | 403 `ORIGIN_NOT_ALLOWED` |

`RefreshRequest` is removed. Same-origin `fetch` sends the cookie by default (`credentials: 'same-origin'`); no CORS credential support is added.

**Cross-site request protection (D3).** `SameSite=Strict` is the first layer. The auth endpoints add an exact `Origin` check against the configured allowed origins (`CORS_ALLOWED_ORIGINS`, which in production is the public origin and locally must include the Compose edge origin `http://localhost`):

- `refresh` and `logout` authenticate with the cookie, so they require an `Origin` header that is in the allow-list; a missing or different `Origin` is 403 `ORIGIN_NOT_ALLOWED`.
- `login` and `register` reject an `Origin` that is present and not allowed (login CSRF); a request without `Origin` (a non-browser client) is accepted, because it cannot carry a victim's cookie.
- A request with `Sec-Fetch-Site: cross-site` is rejected on all four.
- A request carrying more than one `vod_refresh` cookie is treated as invalid (refresh 401, no rotation; login and logout ignore all of them): a cookie with the same name planted by a sibling subdomain must never be chosen by parser order. Host-only cookies do not stop such cookie tossing; this ADR assumes that no subdomain of the deployment's registrable domain is controlled by anyone else. If that assumption cannot hold, the cookie must become `__Host-vod_refresh` with `Path=/` (sent with every same-origin request, still accepted only by the auth endpoints).
- Spring Security's CSRF token mechanism stays disabled: every other endpoint authenticates with the bearer header, which a cross-site request cannot attach.

The check must work behind Nginx on a non-default port; #94 (forwarded host and port) is fixed before it is verified through the edge.

### Sessions, lifetimes and revocation (D4-D6, Issue 6.10)

**Server-side sessions (D4).**

- A new `auth_sessions` table holds one row per signed-in browser session: `id` (the session id), `user_id`, `created_at`, `expires_at` (absolute) and `revoked_at`. Every refresh token belongs to one session (`refresh_tokens.session_id`).
- Login creates a session with `expires_at = now + session lifetime`. Rotation issues the new refresh token in the same session and never extends `expires_at`; the 7-day lifetime is **absolute**, not sliding.
- Presenting a refresh token that was already rotated revokes the **whole session** and returns 401 (replay detection). A rotation whose response was lost therefore ends that session on the next attempt; ADR-011 D2 already accepts this.
- Logout revokes the session. Disabling an account, changing its roles, or an operator's "sign out everywhere" increments `users.auth_epoch` and revokes all of the user's sessions in the same transaction.
- A user has at most 10 active sessions; a new login beyond that revokes the oldest.
- A daily backend job deletes sessions that expired or were revoked more than 30 days ago (their tokens cascade) and legacy tokens without a session, in bounded batches.

**Access tokens (D5).**

- Lifetime 5 minutes by default (`JWT_ACCESS_TOKEN_TTL_MINUTES`, allowed 1-15). Session lifetime 7 days (`JWT_REFRESH_TOKEN_TTL_DAYS`, the absolute session lifetime after Issue 6.10, allowed 1-30). Values outside the bounds fail startup.
- The JWT validator's clock skew is set explicitly to 5 seconds instead of the 60-second default: the issuer and the validator are the same process, so a larger skew only lengthens every token. A stolen access token is usable for at most its lifetime plus that skew, and never after the revocation check (D6) refuses its session.
- New claims: `sid` (the session id) and `ver` (the user's `auth_epoch` when the token was issued), besides `sub`, `userId`, `email` and `roles`. A token without them is rejected (401), so the client refreshes once and receives a new one.
- The player keeps no proactive refresh timer (ADR-011 D2): with a 5-minute token, about one request every 5 minutes of playback takes the 401 → shared refresh → retry path, inside the buffered media.

**Bounded revocation check (D6).**

- After JWT validation, every authenticated request checks that the token's session exists, belongs to `sub`, is not revoked and not expired, that the user is `ACTIVE`, and that `ver` equals the user's current `auth_epoch`. A failed check is 401 `UNAUTHORIZED`, exactly like an expired token, so the client's recovery (ADR-011 D2) refreshes and, for a revoked session, ends it.
- The check reads a bounded in-process cache keyed by session id (Caffeine, managed by Spring Boot's dependency management; this ADR approves the dependency):
  - **Age is measured from the moment the load started**, before the database read: an entry may authorize requests only while `now − loadStart < 30 s`, and is never extended by a hit.
  - Concurrent misses for one key share one load. Each key has an invalidation version; a load whose key was invalidated after the load started is discarded — it neither enters the cache nor authorizes the requests waiting on it, which load again.
  - Logout, epoch changes and session revocations made by the backend invalidate the affected entries after commit.
- **Guarantee:** a change committed at time C — by the backend or by an operator's SQL that the cache never hears about — is enforced for every authenticated API and HLS request that starts after C + 30 seconds, on the single backend instance. Changes made by the backend itself are enforced immediately for requests after the invalidation. Bytes already buffered by the player and requests already authorized are not recalled. Cache expiry and invalidation cause extra loads; on average a busy session costs about one indexed lookup per 30 seconds.
- No cache for: the refresh endpoint (it locks and reads the session and token rows in its transaction) and admin operations (`/api/v1/admin/**` and the admin movie writes), which read the session and user state from PostgreSQL on every request, so a role or account change applies to them at once.
- **Fail closed, but not as an expiry:** if the state cannot be read (a database or pool failure), the request fails with 503 `AUTH_STATE_UNAVAILABLE`, never 401, and no cookie is cleared, so the client keeps the session and shows a retryable error (D7). The current converter's "any runtime exception becomes an invalid token" handling must not swallow this failure. Issue 6.10 declares this 503 on every bearer-authenticated operation of the API contract.
- Movie visibility and the current-asset checks of HLS and playback stay per request and uncached (ADR-011 D4).

### Frontend session lifecycle (D7, Issue 6.9)

- **One protocol for every cookie writer.** Login, refresh (including the bootstrap refresh) and logout each run entirely inside the existing cross-tab Web Lock, from sending the request until its response is handled, because the browser applies `Set-Cookie` before the application sees the response. A request that exceeds its timeout is aborted inside the lock. No other code path calls these endpoints. The current "revoke the unused refresh token" clean-up is removed: with a cookie, logout cannot target an older token and could end the newer session.
- **Persistent generation marker.** A non-secret marker in `localStorage` holds the session generation and the signed-in user id — never a token. Login and logout increment it inside the lock. Every protected request reads it before sending and before committing its result; a response from an older generation or another user is discarded, as today. On `pageshow`, `visibilitychange` and focus a tab reconciles its memory session with the marker. A `BroadcastChannel` carrying no token only wakes other tabs; correctness never depends on it.
- **Bootstrap:** on start the SPA calls `POST /auth/refresh` once (inside the lock). 200 starts the session in memory; 401 means signed out; a network error, a timeout or a 5xx (including 503 `AUTH_STATE_UNAVAILABLE`) shows a retryable error and does not mark the user signed out. The marker lets visitors who never signed in skip the call.
- **Logout that the server has not confirmed.** Logout clears the memory session at once and writes a non-secret "logout pending" flag to the marker. While the flag is set, bootstrap does not refresh; it retries the logout instead, and removes the flag only after the logout returns 204 or when the user explicitly signs in again. The UI says that sign-out is not confirmed and offers a retry while the flag is set. This prevents a reload from silently signing back in with a cookie that a failed logout left behind.
- **Refresh failure classification (moved from Issue 6.6 to Issue 6.9).** Only a refresh rejected with 401 ends the session; a network error, a timeout or a 5xx keeps it and surfaces a retryable error, for JSON requests and bootstrap alike. Issue 6.6 reuses this for HLS requests ([ADR-011 D2](ADR-011.md#player-transport-and-authentication-d1-d4)).
- **Identity change:** a sign-in as another user replaces the cookie for every tab; tabs whose marker shows another user discard their access token and bootstrap again.
- **Legacy cleanup:** the first start of the new version deletes the old `localStorage` session key that holds tokens.
- **Unchanged:** the `ApiClient` single-flight refresh, the one-recovery-per-request budget, and destroying the player on an identity change (ADR-011 D2). `AuthController` keeps the interface the player uses.
- XSS still runs with the page's privileges and can use the in-memory access token while it runs; this design removes long-term token theft, not XSS. The CSP gate in #72/#136 remains required before public deployment.

### Operations and rollout (D8-D9)

**Operations (D8, Issue 6.10).**

- Disabling an account or changing its roles becomes one runbook step that increments `auth_epoch` and revokes the user's sessions in one transaction (`docs/deployment/README.md` is updated with the implementation). It takes effect within 30 seconds (D6).
- `refresh_tokens` and `auth_sessions` have a defined retention (D4); the "Personal data" inventory requested in #72 lists them.
- Logs never contain the cookie or a token; auth events from #139 log the session id only as an identifier.

**Migration, intermediate state and rollout (D9).**

- **Issue 6.9** ships backend, frontend, the API contract (D2: login and refresh `Set-Cookie`, no refresh or logout body, `AuthResponse` without `refreshToken`, `RefreshRequest` removed, 403 `ORIGIN_NOT_ALLOWED`, a `refreshSession` cookie security scheme), the smoke scripts and the Postman collections in one pull request, because the auth contract change is breaking. The contract is not changed in this ADR's pull request: the full-context tests validate every response against it, so it keeps describing the delivered body-based behaviour until the code changes with it. The contract validator does not check cookie attributes or security schemes, so Issue 6.9 tests them directly.
- **State after Issue 6.9, before Issue 6.10:** the refresh token is in the cookie and the access token in memory, but sessions, absolute lifetime, replay revocation of a family, `sid`/`ver`, the session check and the shortened access-token lifetime do not exist yet. The refresh token keeps today's sliding 7-day expiry, the cookie's `Max-Age` follows it, and logout revokes the presented token. Issue 6.10 must land before public deployment.
- **Issue 6.10** adds one new Flyway migration (no existing migration is edited): create `auth_sessions`; add `refresh_tokens.session_id` (nullable, foreign key with `ON DELETE CASCADE`, indexed); add `users.auth_epoch integer NOT NULL DEFAULT 0`. Existing refresh tokens keep `session_id` null and are rejected at refresh, so every signed-in browser signs in once after the upgrade; nothing is deleted by the migration.
- **Configuration upgrade:** `.env.example` and the Compose defaults change `JWT_ACCESS_TOKEN_TTL_MINUTES` from 60 to 5 with Issue 6.10 (60 would now fail startup), and `CORS_ALLOWED_ORIGINS` gains the Compose edge origin with Issue 6.9. The deployment README lists both as upgrade steps.
- **Old bundles:** a tab still running the previous SPA after the upgrade sends a refresh body without a cookie, gets 401 and signs out; reloading loads the new SPA. No compatibility shim is kept.
- The browser end-to-end check (#125) runs after Issue 6.10 against the final model and must observe at least one real HLS 401, a successful refresh and a successful retry, not infer them from elapsed time.

## Options Considered

| Topic | Selected | Alternatives and reason not selected |
|---|---|---|
| Refresh token storage | HttpOnly cookie scoped to `/api/v1/auth` | `localStorage` keeps a long-lived secret readable by any script in the origin. A BFF that also hides the access token adds a server session store and proxies every request, including HLS, for little extra benefit on one origin. |
| Access token storage | Memory only | `sessionStorage` or `localStorage` are readable by the same scripts and survive the tab's lifetime. |
| Cookie scope | Path `/api/v1/auth`, host-only, duplicates rejected, trusted sibling subdomains assumed | `__Host-` resists cookie tossing but requires `Path=/`, which sends the cookie with every API and segment request; it is the fallback if the subdomain assumption fails. |
| CSRF defence | `SameSite=Strict` + exact `Origin` + `Sec-Fetch-Site` on the auth endpoints | Synchronizer tokens need a token readable by scripts and state per session; only four endpoints use the cookie. |
| Cross-tab coordination | One Web Lock for every cookie writer + a persistent non-secret generation marker; `BroadcastChannel` only as a wake-up | A channel alone loses messages for frozen or restored tabs; locking only refresh lets a late login, refresh or logout response overwrite a newer cookie. |
| Revocation | Session + epoch with a 30-second cache aged from load start | Short TTL alone cannot revoke within 30 seconds; a per-JWT denylist still needs a lookup and grows with every token; a per-request uncached query adds a database read to every segment; a user-level epoch alone makes one logout end every device; aging from load completion lets a slow load extend a stale snapshot. |
| Access token lifetime | 5 minutes, 5-second skew | 60 minutes (today) bounds a stolen token badly; 1 minute multiplies refreshes and player recoveries; the default 60-second skew doubles a 1-minute token. |
| Session lifetime | 7 days absolute | A sliding lifetime never ends for an active thief. |
| Replay handling | Revoke the whole session | Rejecting only the replayed token leaves the attacker's successor chain valid. |
| Auth-state failure | 503 `AUTH_STATE_UNAVAILABLE` | A 401 would make an outage look like an expired session. |

## Consequences

- No refresh token is reachable by page scripts; after Issue 6.10 a stolen access token is useful for at most 5 minutes and 5 seconds, and logout, account disabling and role changes take effect within 30 seconds (immediately for admin operations, refresh, and changes the backend makes itself).
- Every page load costs one refresh call; every active tab refreshes about every 5 minutes. Both are small single-row transactions.
- The contract changes are breaking for the auth endpoints only; the SPA, the smoke scripts and the Postman collections change in the same pull request. HLS, playback, progress and every other API keep the bearer header unchanged. Issue 6.10 adds a 503 response to the bearer-authenticated operations.
- A lost refresh response ends the session (the user signs in again); this was already the documented behaviour. A logout the server never confirmed leaves the user signed out locally with a visible retry, instead of a silent re-sign-in.
- The backend gains a scheduled pruning job, an in-process cache and the Caffeine dependency; the single-instance assumption is stated, and a second backend instance would keep the 30-second bound only through cache aging, not invalidation.
- The SPA's refresh-failure classification moves from Issue 6.6 to Issue 6.9.
- ADR-007's body-based delivery is superseded; ADR-011 D3's statement that no cookie carries a token is refined: one cookie carries the refresh token, scoped to `/api/v1/auth`, and no cookie authenticates `/api/v1/*` resources or `/hls/*`.
