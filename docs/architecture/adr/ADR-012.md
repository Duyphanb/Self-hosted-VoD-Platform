# ADR-012: Browser session — HttpOnly refresh cookie, in-memory access token and bounded revocation

Status: Proposed on 2026-11-19 for #72. On 2026-11-19 the owner chose the direction of Q1 and Q2 of the 2026-11-18 system audit as analysed by an independent review: move the refresh token out of JavaScript before the player (Issue 6.6) is built, and add server-side sessions with a bounded revocation delay. The numbers and mechanisms below are the author's proposal. The package becomes the frozen decision when the owner merges it.

## Context

- [ADR-007](ADR-007.md) delivers the refresh token in JSON bodies and deferred an HttpOnly cookie as "post-MVP hardening". The frontend keeps both the access token and the refresh token in `window.localStorage` (`frontend/src/features/auth/AuthContext.tsx:70`, `authStorage.ts`). Any script running in the origin can read a refresh token that lives for 7 days and slides on every rotation.
- The access token lives 60 minutes (`application.yml:54`). Logout revokes only the refresh token (`LogoutService`); the JWT converter trusts the claims and never reads the account (`AccessTokenAuthenticationConverter`). A logged-out, disabled or demoted user keeps every access right until the access token expires.
- A replayed (already rotated) refresh token is rejected, but its successor chain stays valid; there is no session or family, no absolute session lifetime, no per-user session cap and no pruning of `refresh_tokens` (#72, 2026-10-06 comment).
- Issue 6.6 (#223) is about to change the shared `ApiClient` authentication recovery for the hls.js player (ADR-011 D2). Changing token storage after it would rewrite the same code twice, and the browser end-to-end test (#125) should exercise the final session model.
- The owner's principle (2026-11-18): the MVP label is not a reason to keep a weaker design when a better one has a demonstrable benefit at a reasonable cost.

This ADR keeps bearer-header authentication for every API and HLS request (ADR-011 D1-D3), the BCrypt password rules, RBAC with `ROLE_USER`/`ROLE_ADMIN`, and the single backend instance of the single-VPS deployment.

## Decision

### Token placement and transport (D1-D3)

**Refresh token in an HttpOnly cookie; access token only in memory (D1).**

- The refresh token never appears in a response body, a request body, `localStorage`, `sessionStorage` or IndexedDB. The server sets it as one cookie:
  - name `vod_refresh`;
  - `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth`; no `Domain` attribute (host-only);
  - `Max-Age` equal to the remaining absolute session lifetime (D4), so the browser drops it when the session ends.
- `Secure` is on by default. It may be turned off only by explicit configuration whose allowed origins are all loopback origins (local HTTP development); startup fails otherwise, and the production preflight (#138) rejects it. The implementation verifies in Chrome and Firefox that the local `http://localhost` stack works with the chosen setting.
- The `/api/v1/auth` path keeps the cookie off every other request, including `/hls/*`; no cookie ever authenticates an API resource or an HLS request.
- The access token is held in JavaScript memory only. A page reload has no access token and obtains one through the refresh endpoint (D7).

**Endpoints (D2).** Breaking contract changes, shipped together with the frontend in one change (Issue 6.9):

| Operation | Request | Success | Failures |
|---|---|---|---|
| `POST /api/v1/auth/login` | `LoginRequest` (unchanged) | 200 `AuthResponse` (`user`, `accessToken`, `expiresInSeconds`; no `refreshToken`) and `Set-Cookie: vod_refresh=…` for a new session | 400, 401 as today; 403 `ORIGIN_NOT_ALLOWED` (D3) |
| `POST /api/v1/auth/register` | `RegisterRequest` (unchanged) | 201 `UserProfile` (unchanged; registration does not sign in) | 400, 409 as today; 403 `ORIGIN_NOT_ALLOWED` |
| `POST /api/v1/auth/refresh` | no body; the `vod_refresh` cookie | 200 `AuthResponse` and a rotated `Set-Cookie` | 401 `UNAUTHORIZED` for a missing, unknown, expired, revoked or replayed cookie, which also clears the cookie (`Max-Age=0`); 403 `ORIGIN_NOT_ALLOWED` |
| `POST /api/v1/auth/logout` | no body; the cookie when present | 204, idempotent: revokes the cookie's session when there is one and always clears the cookie | 403 `ORIGIN_NOT_ALLOWED` |

`RefreshRequest` is removed. The 128-character input bound now applies to the cookie value: a longer value is treated as invalid (401) before any lookup. Same-origin `fetch` sends the cookie by default (`credentials: 'same-origin'`); no CORS credential support is added.

**Cross-site request protection (D3).** `SameSite=Strict` is the first layer. The auth endpoints add an exact `Origin` check against the configured allowed origins (the existing CORS allow-list, which in production is the public origin):

- `refresh` and `logout` authenticate with the cookie, so they require an `Origin` header that is in the allow-list; a missing or different `Origin` is 403 `ORIGIN_NOT_ALLOWED`.
- `login` and `register` reject an `Origin` that is present and not allowed (login CSRF); a request without `Origin` (a non-browser client) is accepted, because it cannot carry a victim's cookie.
- A request with `Sec-Fetch-Site: cross-site` is rejected on all four.
- Spring Security's CSRF token mechanism stays disabled: every other endpoint authenticates with the bearer header, which a cross-site request cannot attach.

The check must work behind Nginx on a non-default port; #94 (forwarded host and port) is fixed before this is verified through the edge.

### Sessions, lifetimes and revocation (D4-D6)

**Server-side sessions (D4).**

- A new `auth_sessions` table holds one row per signed-in browser session: `id` (the session id), `user_id`, `created_at`, `expires_at` (absolute) and `revoked_at`. Every refresh token belongs to one session (`refresh_tokens.session_id`).
- Login creates a session with `expires_at = now + session lifetime`. Rotation issues the new refresh token in the same session and never extends `expires_at`; the 7-day lifetime is **absolute**, not sliding.
- Presenting a refresh token that was already rotated revokes the **whole session** and returns 401 (replay detection). A rotation whose response was lost therefore ends that session on the next attempt; ADR-011 D2 already accepts this.
- Logout revokes the session. Disabling an account, changing its roles, or an operator's "sign out everywhere" increments `users.auth_epoch` and revokes all of the user's sessions.
- A user has at most 10 active sessions; a new login beyond that revokes the oldest.
- A daily backend job deletes sessions that expired or were revoked more than 30 days ago (their tokens cascade) and legacy tokens without a session, in bounded batches.

**Access tokens (D5).**

- Lifetime 5 minutes by default (`JWT_ACCESS_TOKEN_TTL_MINUTES`, allowed 1-15). Session lifetime 7 days (`JWT_REFRESH_TOKEN_TTL_DAYS`, now the absolute session lifetime, allowed 1-30). Values outside the bounds fail startup.
- New claims: `sid` (the session id) and `ver` (the user's `auth_epoch` when the token was issued), besides `sub`, `userId`, `email` and `roles`. A token without them is rejected (401), so the client refreshes once and receives a new one.
- The player keeps no proactive refresh timer (ADR-011 D2): with a 5-minute token, about one segment request every 5 minutes of playback takes the 401 → shared refresh → retry path, inside the buffered media.

**Bounded revocation check (D6).**

- After JWT validation, every authenticated request checks that the token's session exists, belongs to `sub`, is not revoked and not expired, that the user is `ACTIVE`, and that `ver` equals the user's current `auth_epoch`. A failure is 401 `UNAUTHORIZED`, exactly like an expired token, so the client's recovery (ADR-011 D2) refreshes and, for a revoked session, ends it.
- The check reads a bounded in-process cache keyed by session id: entries expire **30 seconds after they were loaded** (never extended on a hit), concurrent misses for one key share one load, and a load that started before an invalidation never re-populates the cache after it. Logout, epoch changes and session revocations invalidate the affected entries after commit. The cache uses Caffeine (managed by Spring Boot's dependency management); this ADR approves that dependency.
- **The maximum revocation delay for ordinary API and HLS requests is 30 seconds** on the single backend instance. Bytes already buffered by the player and requests already authorized are not recalled.
- No cache for: the refresh endpoint (it locks and reads the session and token rows in its transaction) and admin operations (`/api/v1/admin/**` and the admin movie writes), which read the session and user state from PostgreSQL on every request, so a role or account change applies to them immediately.
- A database failure while loading the state fails the request like any other database failure of that request; a token is never accepted because its state could not be read.
- Movie visibility and the current-asset checks of HLS and playback stay per request and uncached (ADR-011 D4). The session check adds at most one indexed lookup per session every 30 seconds to the HLS path.

### Frontend session lifecycle (D7)

- **Bootstrap:** on start the SPA calls `POST /auth/refresh` once (inside the existing cross-tab lock). 200 starts the session in memory; 401 means signed out; a network error or 5xx shows the retryable state of ADR-011 D2 and does not clear anything. A non-secret `localStorage` hint ("a session probably exists") may skip the call for visitors who never signed in.
- **Cross-tab:** tabs share the cookie but not the access token. Refreshes stay serialized across tabs with the existing Web Lock, so each refresh sends the latest cookie and a parallel refresh cannot look like a replay. Sign-in, sign-out and identity changes are announced on a `BroadcastChannel` that carries no token: on sign-out every tab drops its memory session; on a sign-in as another user every tab discards its access token and bootstraps again, because the cookie now belongs to the new identity. The existing generation guards stay, keyed in memory and on the channel.
- **Legacy cleanup:** the first start of the new version deletes the old `localStorage` session key that holds tokens.
- **Unchanged:** the `ApiClient` recovery and its single-flight refresh, the one-recovery-per-request budget, keeping the session on a refresh network error or 5xx, and destroying the player on an identity change (ADR-011 D2). `AuthController` keeps the interface the player uses.
- XSS still runs with the page's privileges and can use the in-memory access token while it runs; this design removes long-term token theft, not XSS. The CSP gate in #72/#136 remains required before public deployment.

### Operations and rollout (D8-D9)

**Operations (D8).**

- Disabling an account or changing its roles becomes one runbook step that also increments `auth_epoch` and revokes the user's sessions (`docs/deployment/README.md` is updated with the implementation).
- `refresh_tokens` and `auth_sessions` have a defined retention (D4); the "Personal data" inventory requested in #72 lists them.
- Logs never contain the cookie, a token or a session id together with a token; auth events from #139 log the session id only as an identifier.

**Migration and rollout (D9).**

- One new Flyway migration (no existing migration is edited): create `auth_sessions`; add `refresh_tokens.session_id` (nullable, foreign key with `ON DELETE CASCADE`, indexed); add `users.auth_epoch integer NOT NULL DEFAULT 0`. Existing refresh tokens keep `session_id` null and are rejected at refresh, so every signed-in browser signs in once after the upgrade; nothing is deleted by the migration.
- Issue 6.9 (cookie transport, Origin checks, in-memory frontend) ships the backend and frontend changes in one pull request, because the contract change is breaking. It also applies the D2 changes to `API-CONTRACT.yaml` (login and refresh `Set-Cookie`, no refresh or logout body, `AuthResponse` without `refreshToken`, `RefreshRequest` removed, 403 `ORIGIN_NOT_ALLOWED`, a `refreshSession` cookie security scheme). The contract is not changed in this ADR's pull request: the full-context tests validate every response against it, so it keeps describing the delivered body-based behaviour until the code changes with it. Its scripts and collections that call refresh or logout (Newman Sprint 2 auth, `deploy/tests/auth-runtime-smoke.py` and any other smoke that refreshes) switch to a cookie jar and send `Origin`.
- Issue 6.10 (sessions, epochs, bounded revocation, retention) follows; it may land after Issue 6.6, but before public deployment.

## Options Considered

| Topic | Selected | Alternatives and reason not selected |
|---|---|---|
| Refresh token storage | HttpOnly cookie scoped to `/api/v1/auth` | `localStorage` keeps a long-lived secret readable by any script in the origin. A BFF that also hides the access token adds a server session store and proxies every request, including HLS, for little extra benefit on one origin. |
| Access token storage | Memory only | `sessionStorage` or `localStorage` are readable by the same scripts and survive the tab's lifetime. |
| Cookie scope | Path `/api/v1/auth`, host-only | `__Host-` requires `Path=/`, which would send the cookie with every API and segment request. |
| CSRF defence | `SameSite=Strict` + exact `Origin` + `Sec-Fetch-Site` on the auth endpoints | Synchronizer tokens need a token readable by scripts and state per session; only four endpoints use the cookie. |
| Revocation | Session + epoch with a 30-second cache | Short TTL alone cannot revoke within 30 seconds; a per-JWT denylist still needs a lookup and grows with every token; a per-request uncached query adds a database read to every segment; a user-level epoch alone makes one logout end every device. |
| Access token lifetime | 5 minutes | 60 minutes (today) bounds a stolen token badly; 1 minute multiplies refreshes and player recoveries. |
| Session lifetime | 7 days absolute | A sliding lifetime never ends for an active thief. |
| Replay handling | Revoke the whole session | Rejecting only the replayed token leaves the attacker's successor chain valid. |

## Consequences

- No refresh token is reachable by page scripts; a stolen access token is useful for at most 5 minutes, and logout, account disabling and role changes take effect within 30 seconds (immediately for admin operations and refresh).
- Every page load costs one refresh call; every active tab refreshes about every 5 minutes. Both are small single-row transactions.
- The contract changes are breaking for the auth endpoints only; the SPA, the smoke scripts and the Postman collections change in the same pull request. HLS, playback, progress and every other API keep the bearer header unchanged.
- A lost refresh response ends the session (the user signs in again); this was already the documented behaviour.
- The backend gains a scheduled pruning job, an in-process cache and the Caffeine dependency; the single-instance assumption is stated, and a second backend instance would keep the 30-second bound only through cache expiry, not invalidation.
- ADR-007's body-based delivery is superseded; ADR-011 D3's statement that no cookie carries a token is refined: one cookie carries the refresh token, scoped to `/api/v1/auth`, and no cookie authenticates `/api/v1/*` resources or `/hls/*`.
