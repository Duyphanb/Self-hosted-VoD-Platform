# ADR-004: MinIO For MVP Object Storage

Status: Frozen for MVP implementation

## Status

Accepted

## Context

The platform must store large raw video files and generated HLS artifacts. Local filesystem storage inside app containers would be fragile and hard to migrate.

## Decision

Use MinIO as the MVP S3-compatible object storage layer.

Raw uploads, HLS artifacts, and future thumbnails use separate buckets. Optional AWS S3/CloudFront can be introduced later through an adapter without changing core business flows.

## Options Considered

| Option | Pros | Cons |
|---|---|---|
| MinIO | Local and VPS friendly, S3-compatible, portfolio-relevant | Must manage buckets and credentials |
| Local filesystem | Very simple | Poor portability, weak production resemblance |
| AWS S3 first | Production-like | Adds cloud cost and setup before MVP stability |

## Consequences

- Object keys are stored in PostgreSQL.
- Buckets are private by default.
- Backend and worker need MinIO configuration.
- HLS objects stay private and are served only through Nginx `/hls/*` to the backend HLS proxy.
- Future S3 migration should preserve the same storage interface.

## Runtime Addendum

- Addendum (2026-10-29, owner-authorized implementation in #169; review fixes 2026-10-30): backend storage uses `io.minio:minio:9.0.3` behind the SDK-free `ObjectStorage` port in `shared`; the adapter/configuration lives in the `common` assembly. The SDK's OkHttp 5 JVM transport is explicitly selected as `okhttp-jvm:5.3.2` because Maven does not select its Gradle JVM variant. Boot does not manage the complete SDK transitive tree: the backend manages vulnerable Jackson 2, Guava and Snappy versions and excludes unused BouncyCastle, as recorded in [Dependency Security](../../testing/DEPENDENCY-SECURITY.md#managed-version-overrides). This keeps the existing Silo endpoint and private-bucket contract. The SDK exposes known-length InputStream PUT and closeable streaming GET; a fixed 5 MiB part buffer bounds upload memory independently of object size. See [storage identities and policies](../INFRASTRUCTURE.md#storage-identities-and-policies) for IAM, validated configuration, bounded waits and the multipart concurrency safeguard.

- Addendum (2026-10-28, owner-approved in #14): use **PGSTY Silo** as the MinIO-compatible runtime. This addendum is submitted for owner approval through review and merge of the #14 pull request. In frozen documents, “MinIO” denotes the compatible storage protocol and on-disk format; the deployed implementation is now Silo. The service remains `minio`, endpoint `http://minio:9000`, with the existing backend/worker `MINIO_*` environment contract, private `vod-raw`, `vod-hls`, `vod-thumbnails` buckets, named `minio_data` volume and authenticated backend HLS proxy. No storage admin UI or S3 port is public.

### Ownership, licence and trust

The project owner owns digest updates and release/advisory review. PGSTY maintains Silo, principally Feng Ruohang (@Vonng); this is a best-effort project with a concentrated bus factor and no SLA. Monitor [releases](https://github.com/pgsty/silo/releases) and the [security ledger](https://silo.pgsty.com/about/security-advisories/), not just registry availability.

Silo is AGPL-3.0-or-later, used unmodified as an internal network service. Retain its licence/source/NOTICE references; the UBI base has its own licence terms. Mirroring, distributing or modifying the image requires reviewing corresponding-source and network-use obligations. Silo is independent of MinIO, Inc.

Trust rests on PGSTY's tagged GitHub-hosted build and its source revision. Docker Hub is artifact transport, not proof of origin. CI verifies Sigstore/GitHub provenance against the exact signer, source digest and hosted-runner requirement, plus signed SPDX 2.3 SBOMs for both architecture indexes, before image use. Positive verification and a wrong-signer negative control were exercised locally on 2026-10-28. Provenance/SBOM verification does not prove absence of vulnerabilities; the [advisory review](../../testing/DEPENDENCY-SECURITY.md#object-storage-runtime-14) records its limits. CI verification fails closed on unavailable registry/trust services.

At the #14 baseline the server ran as root and apps shared storage root credentials. #169 now provisions independent scoped application identities as recorded above; server non-root operation remains #54. Private buckets, no published storage ports and the disabled console constrain this trust boundary and do not replace the authenticated HLS authorization boundary.

### Compatibility evidence and limits

The pre-change disposable Linux/amd64 spike pulled the digest without a cached image, used the bundled tools, passed curl health checks and init twice, and verified SHA-256 round trips of 100 MiB objects in all three buckets. Anonymous GET/list/PUT returned 403. Objects survived restart and container recreation on the same named volume; re-initialization remained idempotent. With 0.5 CPU / 512 MiB limits, cgroup memory peak was 313,241,600 bytes. Console-off exposed only S3 port 9000 (excluding Docker's DNS listener); the control without `MINIO_BROWSER` exposed a second console port. Storage logs did not contain the test secret.

Repeatable CI evidence is provided by `deploy/tests/storage-runtime-smoke.py` in the unchanged required `Skeleton build checks` job, alongside full-stack startup and Auth/catalog regressions. Local verification results and limitations are recorded in the #14 delivery report. The CI run of the #14 pull request provides the hosted evidence, linked from that pull request when it is opened. Only amd64 was executed; arm64 artifact/provenance metadata was verified. These checks do not certify 2 GiB uploads or upload → transcode → HLS (#125).

### Updates, migration, rollback and exit

Bump the tag/index digest, source revision, signer and SBOM indexes together in a reviewed PR. Read release notes and compatibility/security changes; verify signatures/provenance again, run storage and full-stack smoke, and take an offline backup before starting a new version on existing data. Docker Hub rate limits or artifact retention can affect availability; a mirror is a separate reviewed distribution decision.

No deployment or real upstream-created data exists for this decision. Migration from a volume written by upstream MinIO **was not exercised**; no old upstream binary was downloaded. Silo restart/recreation persistence is not proof of that migration. Before any future migration, test a copy and verify objects, metadata and policies. See the [offline backup/restore runbook](../../deployment/README.md#object-storage-backup-and-restore).

Rollback means restoring a matching offline volume backup **and** its previous digest; an image-only downgrade may misread newer metadata. The exit plan is a separately approved self-build from an audited Silo or maintained compatible fork revision, published to this repository's GHCR with provenance/SBOM and licence compliance, while preserving the storage adapter contract. Never revert to an unpatched frozen upstream release solely because it builds.

### Java SDK selection and maintenance (#169)

The publisher is MinIO, Inc., through the upstream [minio-java repository](https://github.com/minio/minio-java); it is separate from PGSTY's Silo runtime. Reviewed on 2026-10-30, the public repository is not archived and has release/source activity, including the selected [9.0.3 release](https://github.com/minio/minio-java/releases/tag/9.0.3). The SDK is [Apache-2.0](https://github.com/minio/minio-java/blob/9.0.3/LICENSE). The owner monitors upstream releases and security advisories; this selection does not imply a support SLA.

The added runtime footprint includes Jackson 2 alongside Boot's Jackson 3, Guava and annotations, Simple XML, commons-compress/commons-io/commons-lang3/commons-codec, snappy-java, and OkHttp/Okio with Kotlin stdlib. BouncyCastle has no referenced SDK classes and is excluded. Snappy calls occur only in the unused Snowball path, but JVM class resolution still requires its classes when building the client: excluding it reproduced `NoClassDefFoundError`. It is retained at the fixed managed version. The shipped dependency tree and JAR scan, rather than Boot management alone, govern the security review.

The SDK's failed-multipart abort currently joins inside an OkHttp callback. An explicit dispatcher and a smaller bound on active PUTs preserve callback/abort headroom. Named connect/read/write timeouts bound stalls; the shared application client has no total call or GET-body deadline, so steady raw downloads can outlast an individual timeout. Bounded DNS and PUT-admission waits remain. SDK status retries allow five attempts with 100 ms backoff inside the same dispatched call, preserving headroom. Readiness alone keeps its 2 s call/outer deadline, without status retries, and coalesces/caches one actual probe at a time. This mitigates the client-wide deadlock while the upstream bug remains.

Issue 5.2 must carry the dependency overrides/exclusion, named stall timeouts, bounded DNS pool/waits, explicit dispatcher and PUT-admission bound, status retries and safe-exception mapping into its separate worker reactor/client. It must leave total call timeout disabled for raw GET downloads; a 500 MB–2 GB download that steadily transfers data must not fail merely because it lasts over 60 s.

Exit remains possible through an AWS SDK v2 implementation of the same `ObjectStorage` port, preserving callers and business flows. Such a change requires its own dependency/compatibility review and ADR addendum. Silo's exact-prefix force-delete extension would need a separately approved, prefix-conditioned `s3:ListBucket` cleanup mechanism on AWS S3; no such permission or adapter is introduced here.
