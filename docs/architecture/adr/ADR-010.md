# ADR-010: Video asset lifecycle, encoding handoff and media cleanup

Status: Owner-approved decision package on 2026-10-29 for #100, #101, #102, #103, #116 and #117; frozen-document changes take effect through owner review and merge.

Amended 2026-11-01 by the #174 owner decision: upload failure codes, the SPA unknown-result rule and the VPS measurement deferral to #180.

Amended 2026-11-03 by the Sprint 5 worker design owner decision (#103 follow-up, #122, the worker part of #54): [D25-D28](#sprint-5-worker-media-decisions-d25-d28) select the FFmpeg source, the decoder allowlist and probe rules, the output profile, bound and validation, and the worker failure codes and settings.

## Context

Sprint 4 needs one implementable upload contract before its issues are created. The previous documents mixed an asset upsert with multiple asset rows, published before the database commit, left message/ack rules open, and did not define current media or cleanup. A local database transaction cannot atomically commit to RabbitMQ. Large multipart uploads also need explicit edge, temp-disk and browser behaviour.

This decision preserves the modular monolith, a dedicated single-quality worker, private MinIO-compatible PGSTY Silo storage and the authenticated backend HLS proxy behind Nginx. It records the approved design; it does not claim upload, encoding or playback is implemented.

## Decision

### Upload transport and limits (D1-D5)

- Keep `POST /api/v1/admin/movies/{movieId}/video`, one required multipart `file`, and synchronous `202` after raw storage and the asset/job transaction commit. Attempt eager publication before responding; a failed or timed-out publish still returns `202 QUEUED`, because the committed job is the durable handoff record.
- Nest an upload-only regex location inside Nginx `location /api/v1/`, inheriting HTTP/1.1, forwarded headers and API error handling. It has its own `proxy_pass http://backend_upstream;` without a URI, `proxy_request_buffering off` and `proxy_read_timeout 600s`. Keep client-body, client-send and proxy-send inactivity timeouts at 60s. The precise route and checks are in [INFRASTRUCTURE.md](../INFRASTRUCTURE.md#upload-transport).
- Global body limit is `1m`; only the upload route gets `2048m`. `MAX_UPLOAD_SIZE_MB=2048` means MiB. Both Spring multipart limits use the same number, with no extra multipart headroom. The request ceiling includes multipart overhead; a file of exactly 2048 MiB need not fit, while the required 2 GB (2,000,000,000 bytes) file does. Guard equality among Nginx, backend configuration, `.env.example` and the SPA constant in implementation smoke/preflight checks.
- Spring spools to `${TEMP_UPLOAD_DIR:/tmp/vod-uploads}` with threshold `0B`; create and sweep it before the connector accepts requests. Delete only stale regular Tomcat `upload_*.tmp` files immediately inside this dedicated directory, with no recursion or symlink traversal. Reject unsafe directory configuration. Do not use an `ApplicationRunner` for this backend sweep. Request completion/abort releases request temp files. Keep the spool in the backend container layer, without tmpfs or a named upload volume.
- Stream `MultipartFile.getInputStream()` to Silo with `getSize()`, never `getBytes()`. Authorize from headers before multipart parsing. The in-flight DB index limits assets per movie, not simultaneous request bodies or uploads for different movies; #180 measures their combined transient disk use on the target VPS and records the fallback decision (for example an upload-location `limit_conn`). Adopt no limit before that measurement and decision. Global rate/connection limits remain post-MVP.
- Upload declares 401, 409 `VIDEO_UPLOAD_IN_PROGRESS`, 413 `PAYLOAD_TOO_LARGE`, and backend 503/500 failures. 503 `UPLOAD_STORAGE_UNAVAILABLE` (raw storage or spool I/O failed before commit) and 500 `UPLOAD_DATABASE_ERROR` mean the upload was not accepted (no committed asset/job pair; any raw object of this request gets a best-effort delete); manual retry is allowed. 500 `UPLOAD_OUTCOME_UNKNOWN` means the commit could not be confirmed; the raw object is retained and the body is never resubmitted automatically. Any other upload failure returns 500 `INTERNAL_ERROR` with an unknown result. Every error body of this operation, including 401/403, carries `requestId`: the inbound `X-Request-ID` when it matches `[A-Za-z0-9._-]{1,64}`, otherwise a generated UUID. Other routes are unchanged; global correlation remains #139. Edge 413/502/503/504 under `/api/v1/` use `ApiError` JSON; 502/503 use `UPSTREAM_UNAVAILABLE`, 504 `UPSTREAM_TIMEOUT`. Backend JSON passes through unchanged. Once the body was fully sent, any 5xx or network error means the upload result is unknown, unless the `ApiError` `code` is `UPLOAD_STORAGE_UNAVAILABLE` or `UPLOAD_DATABASE_ERROR`: then show a not-accepted failure and allow manual retry. Edge 502/503/504, `UPLOAD_OUTCOME_UNKNOWN`, `INTERNAL_ERROR` and unmapped 500s stay unknown. Never infer acceptance from MovieDetail.videoStatus. A deliberate re-upload is safe: an in-flight asset yields 409 VIDEO_UPLOAD_IN_PROGRESS; if the first upload finished, the new upload creates a newer asset and uses extra storage, reclaimable through the manual purge runbook. Never automatically resubmit the body. A direct newest-asset view follows in #168; add no endpoint here.
- The SPA uses shared `ApiClient.upload()` on XHR: validate size/type/extension, GET the movie first (using the existing token-refresh path), show percent sent, disable duplicate submission, and allow Cancel only while sending the body. At 100% show “Saving to storage…” without Cancel. Never automatically replay an upload after 401; show session expiry. Status 0 means file too large or connection lost; when the outcome is ambiguous, use the unknown-result/manual re-upload guidance above, including when an older READY asset keeps videoStatus READY. An empty `File.type` is filled from the allowlisted extension.
- Demo with 500 MB-1 GB media. Issue 4.6/4.7 records a synthetic 2,000,000,000-byte transport/storage rehearsal in a `workflow_dispatch` job on a GitHub-hosted runner. It is not VPS evidence: it proves neither encoding, ARM throughput nor VPS disk headroom. The genuine 2 GB run on the target ARM VPS belongs to #180, which blocks public deployment: total client time over WAN, saving wait after 100%, backend temp-spool peak, container memory peak and actual VPS disk size/data root. These values are **to be measured in #180**. If saving approaches 600s or disk is insufficient, #180 proposes a separate transport ADR; do not silently change the API.

### Untrusted media handling (D6-D10)

Sprint 4 retains the declared MIME allowlist and adds a signature-family check before storage:

| Declared part MIME | Required signature | Trusted key extension | Worker demuxer |
|---|---|---|---|
| `video/mp4` | ISO-BMFF `ftyp` at offset 4 | `mp4` | `mov` |
| `video/quicktime` | ISO-BMFF `ftyp` at offset 4 | `mov` | `mov` |
| `video/x-matroska` | EBML `1A45DFA3` | `mkv` | `matroska` |
| `video/webm` | EBML `1A45DFA3` | `webm` | `matroska` |

Reject empty/unsupported declarations, family mismatches, text, HLS/ffconcat playlists and legacy QuickTime without `ftyp` with 400 `UNSUPPORTED_VIDEO_TYPE` (empty file remains a validation error). Compatible types within a family are accepted; the extension comes from the validated declaration, never the original filename. Signature checks are fail-fast checks, not a decoder security boundary.

Sprint 5 must force the trusted demuxer and `-protocol_whitelist file`, pass an absolute `file:` input, use typed `ProcessBuilder` argument lists without a shell, disable stdin, clear child environment except `PATH`, `LANG`, `HOME`, bound diagnostic output, and enforce process-tree deadlines and metadata caps. See [SECURITY.md](../SECURITY.md#media-processing-safeguards) for the FFprobe/FFmpeg distinction and residual risk. A codec check on the FFprobe JSON cannot protect decoders opened during probing; FFmpeg's `-codec_whitelist` input option can, and D26 adopts it.

Environment settings are `WORKER_FFPROBE_TIMEOUT_SECONDS`, `WORKER_FFMPEG_TIMEOUT_MIN_SECONDS`, `WORKER_FFMPEG_TIMEOUT_FACTOR`, `WORKER_MAX_DURATION_SECONDS`, `WORKER_MAX_WIDTH`, `WORKER_MAX_HEIGHT` and `WORKER_MAX_STREAMS`. FFmpeg deadline is `max(minSeconds, factor * durationSeconds)`. Timeouts are **to be measured using #124**; research examples are not defaults. D26 fixes the product caps and D28 the settings pipeline. Storage/JDBC calls also require bounded connect/read/statement waits. Check free disk as D27 specifies, before downloading into a dedicated `job-*` directory; delete the raw copy after FFmpeg exits and before uploading HLS.

Issue 5.8 supplies non-root execution, read-only root, a disk-backed writable volume (not tmpfs) for `WORKER_TEMP_DIR`, guarded by the raw-size free-disk check, `cap_drop: ALL`, `no-new-privileges` and `pids_limit` (value validated in that issue). It adds the worker temp volume/mount to [INFRASTRUCTURE.md](../INFRASTRUCTURE.md#persistent-volumes). Stronger per-invocation network/namespace isolation is post-MVP. A decoder compromise can still reach the worker's network, service credentials and process data; the owner accepts this residual MVP risk with these controls, not an unpatched decoder. D25 selects the FFmpeg source and its update procedure. Login/refresh DTO length bounds were a separate follow-up (D10, delivered in #167); Nginx worker tuning is outside this change.

### Sprint 5 worker media decisions (D25-D28)

Owner-approved on 2026-11-03 for #122, the worker part of #54 and the remaining #103 follow-up, after research with FFmpeg experiments and an independent review. FFmpeg 4.4.2 (the current jammy image) and 7.1.5 (Debian trixie) were exercised on amd64; arm64 is measured in #124.

**FFmpeg source (D25).**

- The worker runtime image is `debian:trixie-slim` pinned by digest. It installs Debian `ffmpeg` (component `main`, covered by Debian security advisories; `7:7.1.5-0+deb13u1` from trixie-security on 2026-11-03) and `openjdk-21-jre-headless` from trixie and trixie-security, on amd64 and arm64.
- Apt package versions are not pinned to exact strings, because Debian removes superseded versions from its archive and such a build would break after the next advisory. Instead:
  - every image PR records the installed versions (`dpkg-query -W`);
  - CI asserts a recorded minimum ffmpeg version with `dpkg --compare-versions`;
  - deployments use the built image tag, so rollback redeploys the previous tag.
- The image is rebuilt with `--pull --no-cache` on every Debian security advisory for ffmpeg or openjdk-21, and weekly.
- **Rejected options:**
  - Ubuntu jammy/noble `universe` ffmpeg: the jammy package was last published on 2022-06-08, and later fixes ship only through Ubuntu Pro.
  - Ubuntu Pro: it needs a token in public CI, and its free use is limited.
  - Alpine: it uses musl.
- **CVE policy (no blanket waiver):**
  - Debian can mark ffmpeg CVEs "postponed" between advisories (about 30 on 2026-11-03).
  - Each open ffmpeg CVE in the selected release is assessed for reachability through the demuxers and decoders the worker allows (D26). The assessment is reviewed monthly, and each accepted CVE expires after 90 days unless it is reassessed.
  - When a fix for a reachable CVE exists in another maintained artifact but not yet in Debian, switch to that artifact after confirming it contains the fix. The candidates are Debian bookworm with a separately maintained Temurin 21 JRE, or a checksum-pinned BtbN release-branch build (its GPL variant, for libx264).
- #54 keeps the digest, SBOM and non-root work for the other images, and the container OS-package scan, which first needs a policy for unfixed and postponed CVEs.
- The image contains GPL libx264, so publishing it (#136) is distribution and needs a corresponding-source offer.

**Decoder allowlist and probe rules (D26).**

- FFprobe and FFmpeg both pass `-codec_whitelist` with a decoder list fixed in code, and `-max_streams` with `WORKER_MAX_STREAMS`.
- The list covers these families:
  - video: H.264, HEVC, VP8, VP9, AV1 and MPEG-4 Part 2;
  - audio: AAC, MP3, Opus, Vorbis, AC-3, E-AC-3, FLAC, ALAC and 16/24-bit PCM;
  - text subtitles: `mov_text`, SubRip, ASS and WebVTT.
- The exact names are decoder implementation names from `ffmpeg -decoders` of the D25 binary (for example `mp3float`, `libdav1d`), pinned by a command integration test.
- The allowlist restricts the decoders either tool opens, including during probing. It does not restrict demuxers or parsers. A file with any stream whose decoder is not listed, such as bitmap PGS subtitles, fails as `UNSUPPORTED_MEDIA`.
- After probing:
  - the worker selects the first video stream with `disposition.attached_pic=0` (mapped as `0:V:0`), so cover art is never the video;
  - format and video durations, and the rotation-corrected dimensions, must be finite and positive;
  - rotation comes from the Display Matrix side data (with `tags.rotate` as a fallback), and only 0, 90, 180 and 270 degrees are accepted.

  Any other case fails closed as `UNSUPPORTED_MEDIA` or `PROBE_FAILED`.
- **Product caps (owner policy, not measurements; no 4K sources):**
  - duration ≤ `WORKER_MAX_DURATION_SECONDS=10800`;
  - long side ≤ `WORKER_MAX_WIDTH=1920` and short side ≤ `WORKER_MAX_HEIGHT=1080`, in either orientation, so portrait 1080×1920 is accepted;
  - streams ≤ `WORKER_MAX_STREAMS=8`.

  A violation fails as `MEDIA_LIMIT_EXCEEDED`. There is no fps allowlist: output is capped by `-fpsmax 60`, and the duration-scaled deadline bounds the decode cost of high-fps input.

**Output profile, bound and validation (D27).**

- **Profile (Issue 5.5, #122):**
  - one H.264 High 8-bit `yuv420p` video track: libx264, preset `medium`, CRF 23, with a VBV cap of `-maxrate:v` `HLS_VIDEO_MAXRATE_KBPS` (4000) and `-bufsize:v` twice that;
  - scaled into a 1280×720 box in display orientation (720×1280 for portrait; the long-side limit is `HLS_TARGET_HEIGHT` × 16/9), never upscaled, with even dimensions;
  - `-fpsmax 60`, and keyframes forced every `HLS_SEGMENT_SECONDS`;
  - optional AAC-LC 128 kb/s stereo 48 kHz audio, never copied; a silent source yields video-only HLS;
  - source metadata and chapters dropped;
  - one VOD media playlist `master.m3u8` with MPEG-TS segments under relative `segments/` URIs.
- **HDR:** HDR and 10-bit sources are converted to 8-bit without tone mapping, and the output is tagged BT.709, so players never treat it as PQ/HLG. Their colours look washed out. The owner accepted this as a known limitation on 2026-11-03.
- **Disk bound:** let R be the raw object size, D the probed duration in seconds, and B = ceil(D × `WORKER_OUTPUT_BUDGET_KBPS` × 1000 / 8) + 16 MiB. The budget is 5000 kb/s: 4000 for video, 128 for audio, plus container overhead.
  - Before downloading, free space must be at least R + reserve.
  - After probing, it must be at least reserve + max(B, 2B − R). Temp and Silo share one disk on the single VPS: the raw copy and the local HLS coexist while encoding, then the raw copy is deleted and the HLS exists both locally and in Silo during upload.
  - During encoding and upload, a watchdog checks free space every second. Below the reserve, it kills FFmpeg or stops the upload and fails the job as `INSUFFICIENT_DISK`.
  - `WORKER_DISK_RESERVE_MB` starts at 5120, which also protects the co-located PostgreSQL and Silo data. #124 and #180 calibrate the budget and the reserve.
- **Validation before READY:**
  - FFmpeg runs with `-xerror`, and any non-zero exit fails. Exit 0 is required but not sufficient: FFmpeg exits 0 on a truncated faststart input and writes a shorter HLS that still ends with `#EXT-X-ENDLIST`.
  - The worker checks that:
    - the playlist has `#EXT-X-PLAYLIST-TYPE:VOD` and `#EXT-X-ENDLIST`;
    - it lists at least one segment;
    - every URI matches `^segments/[A-Za-z0-9._-]+\.ts$` and names an existing non-empty file;
    - no unreferenced file is present;
    - the sum of EXTINF durations is within 1 second of the probed duration of the selected video stream, or of the format duration when the stream has none.
  - A failed check is `ENCODE_FAILED`.
  - Before Issue 5.5 merges, #123's valid corpus must show that neither `-xerror` nor the 1-second tolerance rejects a valid file. Changing the tolerance requires such evidence.

**Failure codes and settings (D28).**

- The worker failure-code enum is fixed now:
  - `PROBE_FAILED`, `PROBE_TIMEOUT`, `UNSUPPORTED_MEDIA`, `MEDIA_LIMIT_EXCEEDED`;
  - `ENCODE_FAILED`, `ENCODE_TIMEOUT`;
  - `INSUFFICIENT_DISK`, `STORAGE_ERROR`;
  - `WORKER_INTERRUPTED`, `INTERNAL_ERROR`.

  A DB outage never produces FAILED (D20). #107 adopts this enum and owns the safe messages, redaction and length cap.
- `WORKER_FFMPEG_THREADS=1` is applied as `-threads` and `-filter_threads`. This does not make the whole process single-threaded, and Compose `pids_limit` counts threads.
- Media settings have no application defaults: the worker fails startup when one is missing or invalid.
  - The policy values above are fixed here: caps, VBV, budget, reserve, threads, `HLS_SEGMENT_SECONDS=6` and `HLS_TARGET_HEIGHT=720`.
  - The timeouts come from #124: `WORKER_FFPROBE_TIMEOUT_SECONDS`, `WORKER_FFMPEG_TIMEOUT_MIN_SECONDS` and `WORKER_FFMPEG_TIMEOUT_FACTOR`. #124 runs the Issue 5.5 command line in the worker image on arm64, at the product caps, with a high-entropy source.
  - The first PR that makes a setting required writes its value into `.env.example` and both Compose files, because CI runs `up --wait` with `--env-file /dev/null`.
  - #74 sizes the broker consumer timeout above the probe timeout plus the maximum FFmpeg deadline plus storage time.

### Asset identity, availability and retry (D11-D15, D17)

- Generate a new `videoAssetId` before storage for every upload. Raw key is `{movieId}/{videoAssetId}.{ext}`; PUT raw first, then insert a **new** asset and attempt-1 job together as `QUEUED`. Do not upsert assets. `UPLOADED` remains in enums/CHECKs and the in-flight predicate as a reserved value; this flow never commits it.
- Assign the asset's `created_at` inside the asset/job insert transaction, after the raw PUT and after acquiring per-movie serialization. Never capture it at ID generation or request start: overlapping PUTs must be ordered by the serialized insert, not by upload start time.
- At most one asset per movie may be `UPLOADED`, `QUEUED` or `PROCESSING`. An application pre-check saves a storage write but cannot enforce races. The partial unique index below is authoritative; match its name for the upload 409 and compensate the losing request's raw PUT.
- “Newest” means greatest `(created_at, id)` for the movie. “Current” is the READY asset with greatest `(created_at, id)`, queried once through `findCurrentReadyByMovieId` in encoding. No `movies.current_video_asset_id` column and no worker catalog write are needed. Superseded means READY but not current, or FAILED but not newest.
- `MovieSummary`/`MovieDetail.videoStatus` is READY whenever a current asset exists; otherwise use the newest asset's status; null only when no asset exists. A pending or failed replacement keeps Watch available on the old current asset. Catalog list/detail queries use a catalog-defined port implemented by encoding, or set-based SQL, without a Maven cycle or N+1 queries. The admin asset list's `movieId` filter is contracted now and implemented in Sprint 9, not Sprint 4.
- This package adds no admin current/superseded/eligibility wire fields. Sprint 9 must settle their UI/projection representation before implementation; a paginated subset cannot reliably derive movie-wide classification. The DB rules above are fixed, while additional response fields would need a separate authorized contract update.
- Playback checks movie visibility first (404), then returns 409 `VIDEO_NOT_READY` if no current asset. Playlist and segments require the requested asset to be current and READY, otherwise 404 for missing, hidden, non-ready or superseded assets. Switching current may interrupt an old stream with 404; the viewer reopens playback. Public HLS paths stay unchanged.
- Retry (Sprint 9) requires the newest asset and `FAILED`. Serialize the newest/in-flight check and asset/job transaction per movie (same movie-row lock order for upload commit and retry, plus the partial index). Conditionally set FAILED -> QUEUED, clear failure reason, insert next attempt with `published_at NULL`, and commit before publication. A stale/non-failed asset or a lost double retry returns 409 `VIDEO_ASSET_NOT_RETRYABLE`; one double-click winner returns 202. Missing asset is 404 and authentication is 401. Before Sprint 9, recovery from FAILED uses a new upload.

### Durable handoff (D16)

`encoding_jobs` is its own outbox. One DB transaction commits the asset and job as QUEUED, with `published_at NULL`. Only then publish a persistent message with correlated publisher confirms and mandatory/returns. Confirm success without a return sets `published_at` conditionally when still NULL; it never sets asset/job status back to QUEUED. A fast worker may already have advanced either row.

Defaults are `ENCODING_PUBLISH_CONFIRM_TIMEOUT_MS=5000` and `ENCODING_RELAY_INTERVAL_SECONDS=10`. A single-backend scheduled relay selects QUEUED jobs with `published_at IS NULL` and `queued_at` at least twice the confirm timeout old, oldest first. It republishes until confirmed. Publish failure does not mark FAILED or remove raw media. A confirm-to-DB crash may duplicate delivery, which the worker claim handles. This is at-least-once delivery, not an atomic DB/broker transaction or exactly-once encoding.

### Message, consumer and recovery (D18-D21)

Canonical version-1 JSON (both builds must parse a golden `encoding-job-v1.json` fixture in their implementation tests):

```json
{"schemaVersion":1,"encodingJobId":"6f1d2a4e-8c3b-4a5f-9e7d-1b2c3d4e5f60","videoAssetId":"0b6c1f7e-2a3d-4e5f-8a9b-0c1d2e3f4a5b","attempt":1}
```

- AMQP: `content_type=application/json`, persistent delivery, `message_id=encodingJobId`, optional `x-request-id` header. Fixed DTO JSON; no Java serialization or `__TypeId__` coupling. Ignore unknown fields; reject malformed messages, unsupported versions and job/asset/attempt mismatches to DLQ. A breaking change increments `schemaVersion`. Load storage keys from PostgreSQL, never from the message.
- Durable **classic** queue `${RABBITMQ_ENCODING_QUEUE}` (default `video-encoding-queue`), direct durable DLX `${RABBITMQ_ENCODING_QUEUE}.dlx` and durable classic DLQ `${RABBITMQ_ENCODING_QUEUE}.dlq`. Source queue arguments: `x-dead-letter-exchange=<queue>.dlx`, `x-dead-letter-routing-key=<queue>.dlq`; bind DLQ to that direct exchange with that routing key. Backend and worker declare the identical topology. No DLQ consumer/automatic redrive. No quorum `x-delivery-limit`: the conditional DB claim and startup failure bound processing after a crash.
- Exactly one worker replica, no overlapping containers on recreation, concurrency 1 and env-driven prefetch 1 (`WORKER_PREFETCH=1`). Spring AMQP AUTO acknowledgement returns normally only after a persisted terminal outcome or a safe duplicate skip; `default-requeue-rejected=false`, poison input throws `AmqpRejectAndDontRequeueException`.
- In one short JDBC transaction, validate IDs/latest attempt, conditionally claim job QUEUED -> PROCESSING and asset QUEUED -> PROCESSING, set timestamps, and roll back the pair if either precondition fails. If the claim COMMIT outcome is unknown, hold delivery and read back the job/asset pair once the DB is reachable; a failed conditional re-claim alone is not evidence of a duplicate. If the latest pair is PROCESSING for this encodingJobId and attempt, it is this delivery's own claim under the single non-overlapping worker invariant: continue probe/encode without claiming again, then finish normally. A terminal pair (READY/FAILED), different attempt or newer job is duplicate/stale: acknowledge without media work. If the matching pair is still QUEUED, retry the conditional claim; unresolved/inconsistent readback must not be acknowledged merely because status is no longer QUEUED. No claim token or schema change is needed under this invariant; V5 stays unchanged. Do not hold a transaction during media work.
- In one transaction, conditionally finish both PROCESSING rows to READY (including HLS keys) or FAILED (safe code and timestamps). A genuinely lost finish cleans only its unreferenced attempt prefix and acknowledges; it cannot overwrite a newer state. For a claim use the ownership readback above; if a DB connection fails during the finish commit, read back the pair first: already READY for this job/attempt with these HLS keys is successful completion, not a lost finish, and its prefix must be retained. Every lifecycle transition checks the expected status. DB unavailability at claim/finish retries in-process with capped backoff delays, holding delivery; it must neither return normally, mark media FAILED nor enter the poison DLQ. Do not rerun encoding while retrying the final DB write. A DB outage alone does not trigger retry exhaustion, listener/worker shutdown or startup orphan recovery; consumer-timeout sizing remains #74.
- Worker listener `autoStartup=false`. Before starting it, sweep only owned `job-*` temp directories under a validated `WORKER_TEMP_DIR` (no escaping/symlink traversal), fail orphaned PROCESSING job/asset pairs as `WORKER_INTERRUPTED` in conditional transactions, and best-effort delete those attempt prefixes. Stop startup if DB recovery cannot complete. This is safe only with one non-overlapping worker. Set `stop_grace_period` to 30s; process deadlines kill child trees.
- Backend relay owns unpublished QUEUED work. QUEUED has **no age timeout**: backlog behind the single worker is valid. No backend PROCESSING reconciler/heartbeat columns in MVP. For a wedged JVM, restart worker under the [recovery procedure](../../deployment/README.md#encoding-recovery). Confirmed-message loss after broker data loss, or a corrected DLQ cause with an existing QUEUED job/asset pair, uses that procedure's explicitly approved exact-job `published_at` reset only with an empty source queue and nothing PROCESSING.
- #74 chooses the broker version and sizes/verifies its consumer-timeout handling, including retained delivery during DB-outage retries. RabbitMQ 4.3+ classic queues do not evaluate the consumer timeout; if staying on 3.13, generate/mount a `conf.d` broker `consumer_timeout` from environment above the media-processing deadline measured in #103/#124, with the final sizing left to #74. Do not turn it into an application DB-retry budget or use immutable `x-consumer-timeout` queue arguments. Verify the chosen version with a long job, a second queued job and DB-outage handling; this ADR does not upgrade RabbitMQ.

### HLS objects and cleanup (D22-D23)

HLS keys are `video-assets/{videoAssetId}/attempt-{n}/master.m3u8` and `video-assets/{videoAssetId}/attempt-{n}/segments/*.ts`. Playlists use relative `segments/` URIs. `master.m3u8` is a single VOD media playlist, not a multivariant playlist; Issue 5.5 pins the output profile (D27). Write `hls_bucket`/`hls_master_object_key` only in the successful READY transaction. The backend derives the private prefix from that stored master key and validates `segmentName`; clients still use `/hls/video-assets/{id}/...`.

Automatic cleanup is deliberately small:

1. Issue 4.4 best-effort deletes the exact raw key generated by this request when storage succeeded but the asset/job transaction did not commit (DB failure or 409 loser). On an ambiguous commit response, read back by the generated asset/job IDs before compensation; retain raw while the outcome is unknown. Log WARN with IDs on cleanup failure. A post-commit publish failure is a relay case, never a reason to delete raw.
2. Issue 5.7 best-effort deletes the exact attempt prefix after persisted FAILED, a genuinely lost conditional finish, or startup orphan recovery; also remove per-job temp files on every exit and startup. Read back an ambiguous commit before cleanup; never delete a prefix referenced by a successful READY completion of that same attempt. Cleanup failure cannot undo the terminal DB state.

Retain current raw/HLS, newest FAILED raw for retry, all in-flight objects, and all media on movie archive. Superseded terminal assets may be manually purged only after verifying DB-derived candidates and rechecking current/newest/in-flight status with writers quiesced. Keep DB rows as history; admin views must label superseded rows even if historical keys dangle. Reject bucket roots, non-terminal/current assets and unsafe prefixes; recursive prefixes must end in `/` (`attempt-1/` must not match `attempt-10/`). Log each deletion, run `mc rm --dry-run` first, and scope incomplete multipart cleanup to proven abandoned uploads. See the [purge procedure](../../deployment/README.md#media-purge-and-orphan-audit).

Known limitation: there is **no automatic purge** of retained/superseded media or untracked raw objects left by a crash before the DB commit. Manual candidate review and orphan audit are required; failure compensation is best effort.

### V5 migration specification (D11, D16, D17, D24)

Issue 4.3 adds the next migration (V5 at baseline `24873be`; never edit V1-V4):

```sql
ALTER TABLE encoding_jobs ADD COLUMN published_at timestamptz NULL;
CREATE UNIQUE INDEX ux_video_assets_movie_in_flight
    ON video_assets (movie_id)
    WHERE status IN ('UPLOADED', 'QUEUED', 'PROCESSING');
```

`published_at` has no default/backfill: pre-existing QUEUED rows are eligible for relay and duplicate delivery is safe. Check/report pre-existing duplicate in-flight movies before migration; stop for explicit data repair rather than deleting or choosing a winner. Include the new nullable field in mappings. No current pointer, extra outbox table, heartbeat, optional READY CHECK or extra job index is selected. CI's schema assertion changes `ux`/`ix` indexes 31 -> 32; tables 15, constraints 53, foreign keys 17 and CHECKs 9 remain unchanged. Prove index enforcement and constraint-name-to-409 mapping on PostgreSQL via #119 or an isolated Compose smoke; H2 is insufficient.

## Options Considered

| Topic | Selected | Alternatives and reason not selected |
|---|---|---|
| Upload | Frozen multipart with disk spool | A streaming parser adds non-GA/parser/abort complexity; raw PUT changes the contract; presigned/resumable upload changes scope/public storage; edge buffering doubles spooling and delays auth. |
| Limits | Equal file/request/edge ceilings, route scoped | MAX + headroom and a custom bean add plumbing; global 2 GiB exposes every route; envsubst and auth_request are unnecessary now. |
| Current asset | Derived newest READY | Update-in-place overwrites live media; forbidding replacement loses re-upload; a catalog pointer adds a worker catalog write, FK cycle and stale JPA pointer risk. |
| Availability/retry | READY fallback; newest FAILED only | Newest-status-only hides Watch on a failed replacement; retrying superseded assets wastes work and races current selection. |
| Handoff | Job-row outbox and relay | Publish-before-commit races the worker; compensating FAILED still loses the crash window; a generic outbox duplicates one message type. |
| Consumer | AUTO after persistence, classic/DLX | Manual ack adds channel code; early ack changes recovery semantics; quorum/delivery-limit adds resource cost for one broker. |
| Recovery | Startup fail plus deadlines | An age-based QUEUED timeout fails valid backlog; a backend reconciler cannot unblock a wedged worker; auto-resume needs another crash-loop bound. |
| Media safety | Family check, restricted processes, decoder allowlist, output validation, container controls | MIME alone permits playlists/hangs; codec checks after probing do not isolate decoders, while `-codec_whitelist` narrows decoders but not demuxers or parsers; trusting the FFmpeg exit code accepts truncated output; stronger per-process isolation needs a later spike. |
| FFmpeg source (D25) | Debian trixie packages, rebuilt on each advisory | Ubuntu `universe` ffmpeg is fixed only through Ubuntu Pro; BtbN static builds have no signature or advisory feed (kept as a fallback); Alpine uses musl. |
| Output bound (D27) | VBV cap plus two-step disk check and watchdog | CRF alone has no size bound (about 87 Mb/s measured at 720p on noise); a watchdog alone kills long encodes late. |
| Cleanup | Compensation/failed-prefix cleanup, manual purge | Eager delete-on-supersede is irreversible; a scheduler/ILM adds retention/operations decisions and unverified storage behaviour. |

## Consequences

- Replacement preserves working playback until a new READY asset becomes current, then rejects old HLS immediately. Manual purge can leave historical keys dangling; derived superseded labels must not promise those rows are playable/retryable.
- Disk spooling and the saving wait are accepted tradeoffs requiring measured evidence. Connection counts, encode speed, disk allowances and cap values are not certified by this document.
- Delivery can duplicate; all writers need conditional paired transitions and PostgreSQL race evidence. The relay is part of the backend, not a new service.
- One backend relay and one non-overlapping worker are MVP assumptions. Scaling requires a new recovery/coordination decision.
- R-006/R-007 remain Open until implementation/failure-path evidence exists. #125 alone can establish upload -> transcode -> HLS playback; YAML/build checks prove only the contract and existing code tests.
