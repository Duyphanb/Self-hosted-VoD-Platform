# ADR-009: Catalog visibility, archive retention, and slugs

Status: Accepted; user approved during Sprint 3 contract preparation on 2026-10-02.

## Context

Sprint 3 implements movie CRUD. The frozen contracts left several catalog rules open:

- `SECURITY.md` required a "movie visibility" check for playback and HLS but never defined it. Search, watchlist, rating, and progress had no status rule, so `DRAFT` or `ARCHIVED` movies could leak through later endpoints.
- `BACKLOG.md` required a slug on the admin form, while `UpsertMovieRequest` had none and `movies.slug` is unique and not null.
- Genres were "matched by normalized name" without a definition, while V1 enforces uniqueness only on the raw name and slug.
- `movie_credits` input carried only a name although `people.name` is not unique.
- US-007 requires delete behavior to be explicit before implementation, but the effect of archiving on user-owned records was undefined.

## Decision

Visibility:

- Callers without `ROLE_ADMIN` see only `PUBLISHED` movies. Every endpoint that takes a `movieId` returns the same 404 for a non-published movie as for a missing one. User-facing lists include only `PUBLISHED` movies for every role.
- `ROLE_ADMIN` sees and manages every status on movie detail, update, and archive (`GET`/`PUT`/`DELETE /api/v1/movies/{movieId}`) and under `/api/v1/admin/**`, including `GET /api/v1/admin/movies`. These are the only admin exceptions; admin playback, HLS, progress, rating, and watchlist calls follow the 404 rule. `GET /api/v1/movies` stays published-only for admins too, so its result does not depend on the caller's role.
- The catalog module exposes one visibility check for other modules to reuse.
- A movie may be `PUBLISHED` without a `READY` video asset; clients show that no video is available and hide Watch.

Archive retention:

- Archive is a status change (`DELETE` or `PUT` with `ARCHIVED`); it is idempotent.
- Watchlist items, watch history, playback progress, and ratings are kept. They are hidden while the movie is not `PUBLISHED` and reappear on restore.

Slugs and matching:

- Slug rule: Unicode NFD, remove combining marks, map đ/Đ to d, lower-case, replace each run of characters other than `a-z0-9` with `-`, trim hyphens.
- Movie slugs are required admin input validated against `^[a-z0-9]+(-[a-z0-9]+)*$`. The backend never generates or rewrites them. A duplicate returns 409 `MOVIE_SLUG_CONFLICT`. Routes use the movie UUID.
- Genre names are trimmed with whitespace collapsed. The genre slug is derived from the name and is the match key, so case, spacing, and diacritic variants map to one genre without a new migration. Renaming a genre recomputes its slug.
- Person names are trimmed with whitespace collapsed before storage. Person slugs are generated by the server with the slug rule, the base truncated to at most 240 characters (base `person` when the rule yields nothing), plus a `-2`, `-3`, ... suffix on collision; a rename excludes the person itself from the collision check.
- Credits identify a person by `personId`. Name-only input is compared case-insensitively, with diacritics significant, against the stored names of all people: no match creates a person, exactly one match reuses it, and two or more return 400 asking for a `personId`.

## Consequences

- No Flyway migration is needed; CI schema counts stay unchanged.
- Names that differ only by diacritics (for example `Hài` and `Hai`) are one genre.
- Adding a second person with an existing name requires creating that person first and sending its `personId`.
- Sprints 5-8 must call the catalog visibility check for playback, HLS, progress, rating, watchlist, history, and search, with 404 tests for `DRAFT` and `ARCHIVED` movies.
- The search vector logic must rebuild vectors on genre and person renames and backfill movies created before it exists.
- H2 test schemas come from entities; slug uniqueness, locking, and constraint-to-409 mapping also need PostgreSQL runtime evidence.
