# ADR-011: Authenticated HLS playback, player behaviour and playback progress

Status: Proposed on 2026-11-14 for #104, #105, #107 and #126. The owner chose D9, D10 and D17 on 2026-11-14; the other decisions are the author's proposal. On 2026-11-17 an independent review of the whole package revised D2, D4, D7, D9-D11, D13 and D17. The package becomes the frozen decision when the owner merges it; until then `main` still documents the Redis progress buffer.

## Context

Sprint 5 delivers READY HLS objects in the private `vod-hls` bucket. Sprint 6 adds the authenticated HLS proxy, the browser player and playback progress. Before its issues are created, four open design issues had to be settled:

- **#104:** the player must send the bearer token on every playlist and segment request, yet the access token (60 minutes by default) can expire during a movie, and only `ApiClient` knew how to refresh it. The documents still allowed "HLS.js or Video.js", although native HLS playback cannot send an `Authorization` header.
- **#126:** the player had no browser matrix, accessibility rule, error mapping or start-position rule.
- **#105:** progress was specified as a Redis write-behind buffer flushed every 30-60 seconds. Reads skipped the buffer, the flush could lose updates, Redis durability was undefined, `watch_history` had no owner, and "finished" was entirely client-controlled. The backend has no Redis client today.
- **#107:** BACKLOG acceptance criteria, OBSERVABILITY and the frozen API contract disagreed in several places.

[ADR-010](ADR-010.md) already fixed the HLS layout (D22, D27: `master.m3u8` is one VOD media playlist with relative `segments/seg_NNNNN.ts` URIs, validated before READY), the current-asset rule (D14: 404 for non-current assets, 409 `VIDEO_NOT_READY` without a current asset) and the worker failure codes (D28). This ADR does not change them.

This decision preserves the modular monolith, the single public edge, private buckets and the authenticated backend HLS proxy. It records the approved design; it does not claim that playback or progress is implemented.

## Decision

### Player transport and authentication (D1-D4)

**hls.js only (D1).**

- The player uses [hls.js](https://github.com/video-dev/hls.js), pinned to an exact version in `frontend/package.json` (1.7.4 when this ADR was written; never below 1.5.0, the first release with ManagedMediaSource support).
- The player checks `Hls.isSupported()` first. When it is true, the player attaches hls.js to the `<video>` element and loads `PlaybackInfo.hlsManifestUrl`. When it is false, the player shows the unsupported-browser state (D7).
- The manifest URL is never assigned to `video.src` or a `<source>` element, and `canPlayType` is never used to choose a native path. Native HLS playback cannot send the `Authorization` header, so it would fail with 401 on every request; current Chromium also answers `canPlayType` positively for HLS, so native-first detection would break Chrome.
- Video.js is not used: by default its HLS engine hands playback to the native player on Apple browsers.
- AirPlay and other remote playback are unsupported in the MVP. Under ManagedMediaSource hls.js disables remote playback on the element. Supporting native playback or AirPlay needs a new ADR, for example a per-video short-lived media token; it must not be solved with a token in the URL (D3).

**Token per request, one refresh, one retry (D2).**

- Every playlist and segment request reads the current access token when it is sent and sets `Authorization: Bearer <token>` (hls.js `xhrSetup`, which may return a promise). Requests never use cookies or `withCredentials`.
- The player and the JSON API share one session and one authentication recovery. `ApiClient` exposes the recovery it already uses for JSON requests, given the token that received the 401: if the current token is already a different one (a late 401 of an old token), retry with the current token without refreshing; otherwise join the single-flight refresh. The player never calls the refresh endpoint on its own.
- Each HLS request has one recovery budget: one recovery and one retry. In hls.js the retry is the `shouldRetry` hook of the manifest, playlist and fragment load policies (hls.js does not retry a 4xx by default), and the retried request waits for the recovery in `xhrSetup`. If a 401 still surfaces as a fatal network error, the error handler restarts loading at the current position only when that request's budget is unused; it never grants a second recovery.
- The session has expired only when the retry with the current token still gets 401, or when the server rejects the refresh with 401. Then the player stops loading and the application's authentication-failure path runs (clear the session, go to login).
- A refresh that fails by a network error, a timeout or a 5xx response does not prove that the session expired: the session is kept and the player shows the network-error state with Retry. The same rule applies to JSON requests, which today clear the session on any refresh failure; Issue 6.6 changes this shared `ApiClient` behaviour. A refresh token already rotated by a lost response is then rejected with 401 on the next attempt, which ends the session normally.
- When the signed-in identity changes (logout, or another account in another tab), the player is destroyed. A stream never continues under a different identity, and a callback of an old identity never ends a newer session.
- A long pause needs no timer: the first request after the pause follows the 401 rule.

**No token in a URL (D3).**

- The resource server accepts the bearer token only in the `Authorization` header. An `access_token` query or form parameter is never accepted, on `/hls/*` or `/api/v1/*`, and no cookie carries a token.
- A backend test proves it: a request with a valid token in `?access_token=` and no header returns 401.
- The frontend never puts a token into a URL and never uses `navigator.sendBeacon` for authenticated calls (it cannot send the header).
- Do not copy the stream-URL API key or cookie-plus-`auth_request` models of other self-hosted media servers; both contradict [SECURITY.md](../SECURITY.md#hls-access-control).

**HLS proxy responses (D4).**

- A successful playlist or segment response is 200 with the whole object. `Content-Type` is `application/vnd.apple.mpegurl` for `master.m3u8` and `video/mp2t` for a segment. `Content-Length` is sent when the storage read reports the object size.
- Every HLS response, including error responses, carries `Cache-Control: no-store`. The responses are authenticated, the next request after a current-asset switch must be refused, and a shared browser must not serve one user's media from its cache after logout. Nginx does not cache `/hls/*`.
- `Range` is not supported: the playlist has no byte ranges and the player requests whole segments. A `Range` header is ignored and the full 200 response is returned.
- Every request re-checks the JWT, the movie visibility and that the asset is the current READY asset (ADR-010 D14). Segment names must match `^[A-Za-z0-9._-]+\.ts$` before storage is read.
- Errors are `ApiError` JSON:
  - 401 `UNAUTHORIZED` for a missing or invalid token;
  - 404 `VIDEO_ASSET_NOT_FOUND` for a missing, hidden, non-READY or superseded asset, a `videoAssetId` that is not a UUID, an invalid segment name and a missing object. The application's own validation of the asset ID and segment name returns 404, never 400, so every not-found case looks the same. A request malformed below the application (rejected by Nginx, the servlet container or the security filters) may still get their own 400;
  - 503 `HLS_STORAGE_UNAVAILABLE` when storage cannot be read before the response starts. hls.js retries 5xx responses with backoff. A failure after the response started aborts the connection.
- Internally the backend distinguishes the cases that share the public 404: a current READY asset whose object is missing is an integrity problem and is logged at WARN with the asset ID, unlike an access that is simply not allowed. The `ObjectStorage` port today maps every read failure to one `IOException`; Issue 6.2 makes it distinguish a missing object (404) from unavailable storage (503), and closes the storage stream when the client disconnects.
- Nginx keeps forwarding `Authorization` and `X-Request-ID` on `/hls/` and adds no CORS headers: the SPA and the HLS paths share one origin. Edge-generated errors on `/hls/*` are not JSON; the player reads only the status.
- An HLS authorization failure is logged with the request ID and asset ID, never with the token.

### Player specification (D5-D8)

**Browser matrix (D5).** NFR-005 ("modern desktop browser") is unchanged; this table defines what is verified.

| Browser | Playback path | Level |
|---|---|---|
| Chrome or Edge, current stable, desktop | hls.js (MSE) | Verified: one manual row at the sprint closeout, with the version recorded |
| Firefox, current stable, desktop | hls.js (MSE) | Verified: one manual row at the sprint closeout, with the version recorded |
| Safari on macOS | hls.js (MSE or ManagedMediaSource) | Best effort |
| Safari on iPadOS 13 or later | hls.js (MSE or ManagedMediaSource) | Best effort |
| Safari on iPhone, iOS 17.1 or later | hls.js (ManagedMediaSource) | Best effort |
| Safari on iPhone before iOS 17.1 | none | Unsupported-browser state |
| Chrome or Firefox on iOS and iPadOS | WebKit, so the same as Safari on that device | As the Safari row |
| Any browser where `Hls.isSupported()` is false | none | Unsupported-browser state |

"Best effort" means the path is expected to work but is not part of the Definition of Done; a defect there is tracked, not blocking. The frontend adds no browserslist or `build.target` change. A unit test proves that a browser answering `canPlayType` positively for HLS still takes the hls.js path.

**Controls and accessibility (D6).**

- The player is a native `<video controls playsinline>` element with `aria-label` set to the movie title. There is no custom control bar, skin or hotkey layer, so keyboard and screen-reader support comes from the browser.
- No `autoplay` attribute. Captions are out of scope.

**Error state machine (D7).**

- Only an error with `data.fatal === true` leaves the playing state. Non-fatal hls.js errors are routine and never change the UI.
- Fatal `MEDIA_ERROR`: call `recoverMediaError()` once per player instance. A second fatal media error shows the playback-error state.
- Fatal `NETWORK_ERROR`, by HTTP status:
  - 401: the D2 rule;
  - 404: the asset is no longer current or the movie is no longer visible. Fetch the playback info again once. If it returns a different `videoAssetId`, reload the player with the new manifest at the current position; if it returns 404 or 409, show "This video is no longer available"; if the refetch fails by a network error or a 5xx, show the network-error state with Retry;
  - any other status, or no status: show the network-error state with a Retry action that restarts loading at the current position.
- A fatal codec or container incompatibility, and `Hls.isSupported()` being false, show the unsupported-browser state. Any other fatal error shows the playback-error state. A fatal state destroys the hls.js instance.
- Live regions: the initial load is announced with `role="status"`; a fatal state uses `role="alert"`; the rebuffering spinner is `aria-hidden`, so buffering is not announced repeatedly.
- The watch page maps the playback API: 404 `MOVIE_NOT_FOUND` shows the not-found state, and 409 `VIDEO_NOT_READY` shows the viewer-facing availability label ("Processing" or "Not available"). Failure codes and messages are never shown to viewers (D18).

**Start position and autoplay (D8).**

- The player loads paused at `PlaybackInfo.resumeSeconds` through the hls.js `startPosition` setting (the default when `resumeSeconds` is 0). It never calls `play()` on its own: the viewer starts playback with the native controls.
- A rejected `play()` promise (for example `NotAllowedError`) leaves the player paused and is never an error state.
- At the end the player sends the final progress update (D13) and stays on the last frame; there is no auto-next.

**Test cases (copied into Issues 6.6 and 6.7).**

- Automated browser smoke, part of #125 (decided 2026-11-17): Playwright (`@playwright/test`, a pinned frontend devDependency with its own `test:e2e` command and config, outside Vitest) drives one scenario in desktop Google Chrome (`channel: 'chrome'`; the bundled Chromium may lack H.264/AAC). Setup goes through the API behind Nginx on an isolated Compose stack: a test admin, a published movie, the upload of a generated clip of about 120 seconds with audio through the real worker, and a bounded wait for READY. The browser then logs in and opens the real watch page, with nothing mocked. It checks that playback starts paused, starts it by a user action, and observes at least 60 seconds of media time advancing at normal rate before any seek, with growing decoded frames and no media error. The stack uses a one-minute access-token lifetime so that playback crosses at least one expiry and must continue through the D2 recovery. It then seeks, pauses, resumes, waits for a successful progress save below the 90% threshold, reloads and checks the resume position. It first checks that the browser can decode H.264/AAC and fails, never skips, when it cannot. Traces, HAR files and stored sessions stay off; diagnostics are an allowlist (browser version, media error code, timestamps, route and status), with no header, body or token. It runs locally and by `workflow_dispatch`; one successful run is recorded at the sprint closeout before it becomes a check on pull requests. It does not replace the manual rows below.

- Manual, one row per verified browser: 60 seconds of playback, a seek, pause and resume, then a reload that resumes near the last position.
- Manual keyboard-only pass: reach the player, play, pause, seek, change volume and enter fullscreen without a pointer.
- Unit tests (the save triggers of D13 have their own fake-timer test, including a pause followed by `ended` within the same second): a non-fatal error keeps the state; one `recoverMediaError()` for a fatal media error and the error state for the second; 401 recovers once, retries once and expires the session on a 401 after the retry; a late 401 of an old token retries with the current token without a refresh; a refresh that fails with 503 keeps the session and shows Retry; an account change during a refresh destroys the player without ending the new session; the load-policy retry and the fatal handler never recover twice for one request; 404 with a new current asset reloads and 404 without one shows "no longer available"; the unsupported state when `Hls.isSupported()` is false; the hls.js path when `canPlayType` answers positively; `video.src` is never set to the manifest URL; the start position equals `resumeSeconds`; a rejected `play()` stays paused.

### Playback progress (D9-D14)

**Direct PostgreSQL write, no Redis buffer (D9).** Owner decision on 2026-11-14.

- `PUT /api/v1/movies/{movieId}/progress` runs one short transaction: the catalog visibility check (404), the current READY asset lookup (409 `VIDEO_NOT_READY` without one), a check that the request's `videoAssetId` (from `PlaybackInfo`) names that current asset (409 `VIDEO_ASSET_NOT_CURRENT` otherwise, so a save from a replaced stream is never interpreted against the new asset), a forward-only upsert of `playback_progress`, the `watch_history` upsert (D12), then commit. The response is 200 with the stored state. No progress exists only in memory or in a cache.
- The upsert keeps the newest write by server time:

  ```sql
  INSERT INTO playback_progress
      (user_id, movie_id, current_seconds, duration_seconds, finished, last_played_at, created_at, updated_at)
  VALUES (:userId, :movieId, :currentSeconds, :durationSeconds, :finished, :now, :now, :now)
  ON CONFLICT (user_id, movie_id) DO UPDATE
  SET current_seconds = EXCLUDED.current_seconds,
      duration_seconds = EXCLUDED.duration_seconds,
      finished = EXCLUDED.finished,
      last_played_at = EXCLUDED.last_played_at,
      updated_at = EXCLUDED.updated_at
  WHERE playback_progress.last_played_at <= EXCLUDED.last_played_at;
  ```

  `:now` comes from the application `Clock`. The position may move backwards (a seek back); only `last_played_at` is forward-only. When the guard rejects an older write, the response returns the stored newer row.
- The guard orders writes by server arrival, not by when the viewer acted. A save that waits for a token refresh can therefore arrive after a newer one. D13 prevents this within one player by sending at most one save at a time. Between tabs or devices playing the same movie, the last save to arrive wins; this is an accepted MVP limitation. `MAX(current_seconds)` is not used, because seeking back is valid.
- The write rate is an assumption to measure, not a proven property: N viewers produce about N/10 small transactions per second. The k6 measurement before deployment confirms it on the target VPS.
- There is no flush service, dirty marker or buffer TTL. Issue 6.4 is withdrawn.
- The existing V1 tables, primary key and indexes are sufficient. No migration is added.
- Redis stays in the stack as the reserved cache. No Sprint 6 component uses it, and it never holds durable user state. The first feature that adds a Redis client must authenticate with `REDIS_PASSWORD` and make the server explicitly ephemeral in the same change (`--save ""`, no data volume, `maxmemory` with an eviction policy).

**Completion and clamping are server-derived (D10).** Owner decision on 2026-11-14; the resume consequence was revised on 2026-11-17 (D11).

- Let D be `duration_seconds` of the movie's current READY asset.
- `currentSeconds` is clamped to `[0, D]`.
- `finished` is true when the request says `finished: true` (the player's `ended` event; the server then stores the position as D) or when `currentSeconds × 10 ≥ D × 9` after clamping, that is at 90% of the duration. The threshold is owner policy and a code constant, not a setting.
- `finished` means "counts as watched" for watch history and Continue Watching. It does not decide where playback resumes (D11). The `ended` flag is the client's report, not proof that every frame was watched; that is acceptable for personal progress.
- The request's `durationSeconds` stays in the contract for compatibility and is ignored. The stored `duration_seconds` is D.
- If D is unknown (a READY asset without a stored duration), nothing is clamped and only the request flag sets `finished`.
- A later update below the threshold with `finished: false` clears `finished`: the viewer is watching again.

**Read rules (D11).**

- Every read normalizes the stored row against the current asset in the same way: when a current asset with a known D exists, the position is clamped to D and `durationSeconds` is D.
- `PlaybackInfo.resumeSeconds` is 0 when there is no progress row, or when the normalized position equals D: playback reached the end, or a shorter replacement ends before the stored position. Otherwise it is the normalized position, also for a movie that is finished at 90%: a viewer who stopped with 12 minutes left resumes there, and can seek back to the start with the native controls. When D is unknown, `resumeSeconds` is 0 for a finished row and the stored position otherwise. `PlaybackInfo.durationSeconds` is D.
- `GET /api/v1/movies/{movieId}/progress` returns the normalized row. Without a row it returns `currentSeconds: 0`, `finished: false`, `durationSeconds: null` and `lastPlayedAt: null`. The visibility 404 applies; a current asset is not required (without one the stored row is returned unchanged).
- `GET /api/v1/me/continue-watching` returns the caller's rows that are not finished, whose normalized position is above 0 and below D, and whose movie is PUBLISHED with a current READY asset. Ownership, visibility and these conditions apply before ordering by `last_played_at` descending, then `movie_id`, and the limit of the 50 most recent. Each item carries the normalized progress, so a card and the playback it opens agree. It stays an array; the page says it shows the 50 most recently watched movies and has no pagination.

**Watch history ownership (D12).**

- The progress write owns `watch_history`. In the same transaction, an accepted progress write inserts the history row on the first update (`started_at = last_watched_at = now`) and otherwise advances `last_watched_at`. `completed_at` is set once, when a stored update is first finished, and is never cleared.
- When the forward-only guard rejects a progress write, history is not touched.
- Issue 8.2 only reads history.

**Client save triggers (D13).**

- While playing, the player saves every 10 seconds (within the 5-10 second NFR target). It also saves on pause, after a seek, on `ended` (with `finished: true`), when the page becomes hidden (`visibilitychange`), on `pagehide` and when the player unmounts.
- Positions are whole seconds, rounded down. Nothing is saved before playback first starts, so opening the watch page creates no history. A save is skipped only when its whole payload, the position and `finished`, equals the last successful save. The `ended` save is therefore always sent, even when a pause in the same second already saved that position: the stored duration is rounded up, so the last whole second can lie below the 90% threshold.
- Each save carries the `videoAssetId` of the stream being played. At most one save is in flight per player: a trigger that fires while a save runs replaces a single pending snapshot, which is sent when the running save completes, so a save that waits for a token refresh can never overwrite a newer position from the same player.
- Regular saves go through `ApiClient` (shared authentication recovery, D2). They never interrupt playback: a failed save is retried at the next trigger and shows no error. A 404 or 409 `VIDEO_NOT_READY` stops further saves; a 409 `VIDEO_ASSET_NOT_CURRENT` stops them and makes the page fetch the playback info again, as for an HLS 404 (D7).
- Saves at unload use `fetch` with `keepalive: true`, the latest snapshot and the current token, without refresh or retry, even when another save is in flight; such a save is best effort and may be lost. `sendBeacon` and query-string tokens are forbidden (D3).

**Replacement (D14).** Progress is keyed by user and movie, so it survives a video replacement. Clamping, completion and resume always use the current asset.

### Contract reconciliation (D15-D18)

**Statuses and codes (D15).**

| Operation | Declared now |
|---|---|
| `GET /movies/{movieId}/playback` | 400 `VALIDATION_ERROR` for a `movieId` that is not a UUID; 404 `MOVIE_NOT_FOUND`; 409 `VIDEO_NOT_READY` |
| `GET /hls/video-assets/{videoAssetId}/...` | 401; 404 `VIDEO_ASSET_NOT_FOUND`; 503 `HLS_STORAGE_UNAVAILABLE` |
| `GET /movies/{movieId}/progress` | 400 `VALIDATION_ERROR`; 404 `MOVIE_NOT_FOUND` |
| `PUT /movies/{movieId}/progress` | 200 instead of 202 (the write is committed, not buffered); 400; 404; 409 `VIDEO_NOT_READY` or `VIDEO_ASSET_NOT_CURRENT`. `ProgressRequest` gains the required `videoAssetId` |
| `GET /admin/video-assets` | 400 `VALIDATION_ERROR` for an invalid filter or page parameter |
| `POST /admin/video-assets/{videoAssetId}/retry` | 400 `VALIDATION_ERROR`; 404 `VIDEO_ASSET_NOT_FOUND` |

`info.version` stays `1.0.0-frozen`, as in earlier authorized contract changes; the contract description names this ADR.

**BACKLOG reconciliation (D16).**

- Issues 6.1-6.8 follow this ADR. Issue 6.3 uses the camelCase `ProgressRequest` fields and owns `GET` and `PUT` progress and the history write; Issue 6.4 is withdrawn; Issue 6.8 shows the array without pagination.
- Issues 6.3, 6.5, 7.3, 7.4, 8.1, 8.2 and 8.3 gain a criterion to use the catalog visibility check (ADR-009), with integration tests for DRAFT, ARCHIVED and missing movies for ROLE_USER and ROLE_ADMIN. An operation that takes a `movieId` (progress, watchlist add and remove, rating) returns 404. A list (continue watching, search, suggestions, watchlist, history) returns 200 with only PUBLISHED movies, and an empty result when nothing matches.
- BACKLOG 9.1 and 9.3 already match the contract (retry 202/409, the `movieId` filter). Issue 9.1 now implements the D17 projection.
- The rating count and watchlist pagination drift stays with #130, and the search cache conflict with #128.

**Admin asset projection (D17).** Owner decision on 2026-11-14; implemented in Sprint 9.

- `VideoAssetAdmin` gains these fields, all computed by the server for each row from the movie-wide state, never from the returned page:
  - `failureCode`: the ADR-010 D28 code, or null;
  - `queuedAt`, `startedAt`, `finishedAt`: the timestamps of the asset's latest attempt;
  - `retryEligible`: true only for the newest asset of its movie when it is FAILED. It is a snapshot for the UI, not a promise: the retry endpoint re-checks atomically and can still answer 409;
  - `superseded`: true for a READY asset that is not current and for a FAILED asset that is not newest.
- `retryEligible` and `superseded` are required in every item.
- `failureReason` is the fixed safe message of `failureCode` (D18).
- The list has a total order: `createdAt` descending, then `id` descending. The `movieId` and `status` filters combine.

**Failure messages and redaction (D18).**

- `video_assets.failure_reason` and `encoding_jobs.error_message` hold only the D28 code name (at most 32 ASCII characters). They never hold free text, paths, object keys, host names or tool output. The worker already writes only the code.
- The backend maps the code to a fixed English message when it builds an admin response; an unknown stored value is reported as `INTERNAL_ERROR`. Diagnostics stay in the worker logs, bounded, with `encodingJobId` and `videoAssetId`.
- The message table is in [OBSERVABILITY.md](../OBSERVABILITY.md#failure-visibility). Viewers never see a failure code or message.

## Options Considered

| Topic | Selected | Alternatives and reason not selected |
|---|---|---|
| Player engine | hls.js only, no native path | Video.js defaults to native HLS on Apple browsers; native playback and AirPlay cannot send the bearer header; native-first detection breaks Chrome. |
| Player authentication | Header per request, shared refresh-once, one retry | A token in the URL leaks into logs and history; cookies plus `auth_request` change the auth model and need CSRF handling; a per-video media token is a new mechanism, kept for a later ADR if native playback is needed. |
| 401 handling | Shared `ApiClient` recovery with one budget per request, load-policy retry, error handler only within that budget; only a confirmed rejection ends the session | A proactive refresh timer duplicates session logic and still races; restarting the player on every 401 interrupts playback; logging out on a refresh network error ends sessions that are still valid. |
| HLS caching | `no-store` | Private caching would serve media after logout on a shared browser and delay a current-asset switch; the proxy cost is acceptable for the single-quality MVP. |
| Controls | Native `<video controls>` | A custom control bar needs its own keyboard, focus and screen-reader work and tests. |
| Autoplay | Load paused at the resume position | `play()` without user activation is rejected on deep links and reloads. |
| Progress storage | Direct PostgreSQL forward-only upsert | The Redis write-behind buffer saves no round trip (each update already reads PostgreSQL for visibility) and adds a loss window, merged reads, an atomic clear and Redis durability rules. One small transaction every 10 seconds per viewer is expected to be cheap at the NFR scale; k6 measures it before deployment. |
| Progress ordering | Server arrival order, one save in flight per player | Client sequence numbers add contract and storage for a multi-device case the MVP accepts; `MAX(current_seconds)` breaks seeking back. |
| Progress asset context | Required `videoAssetId`, 409 for a replaced asset | Interpreting every save against the current asset lets a replaced stream's `ended` mark the new asset finished. |
| Completion | Server-derived at 90% of the current asset, plus the client `ended` flag; resume stays at the saved position | A purely client-controlled flag has no threshold or clamp; restarting from the beginning after 90% loses up to a tenth of the movie (12 minutes of a two-hour film); 95% only moves that loss. |
| Watch history | Written by the progress transaction | A separate writer (flush job or Issue 8.2) can disagree with progress. |
| Admin failure fields | Additive contract fields computed per row | Relaxing OBSERVABILITY hides retry eligibility; deriving it in the UI from one page is unreliable (ADR-010). |
| Failure text | Stored code plus a fixed message table | Free-text reasons can leak paths, keys or tool output and cannot be translated or tested. |

## Consequences

- Every playlist and segment request costs a token validation and two small queries. After a current-asset switch, or once the movie is hidden, the next playlist or segment request is refused; media the player has already buffered can still play to the end of that buffer.
- Browser HTTP caching of media is disabled. Seeking back into evicted buffer downloads segments again.
- iPhone before iOS 17.1, AirPlay and casting are unsupported until a later decision.
- Progress durability no longer depends on Redis; an accepted update is committed. NFR-006, US-011, R-015 and the Sprint 6 Definition of Done change accordingly, and Redis has no consumer until a cache feature needs it.
- `PUT progress` answers 200 with the stored state, and 409 when the movie has no playable asset or the save names a replaced asset.
- A movie counts as watched at 90% for history and Continue Watching, but reopening it resumes at the saved position; only playback that reached the end restarts from the beginning.
- Saves for one movie from several tabs or devices resolve by server arrival order.
- A refresh that fails by a network error keeps the session for JSON requests too, which changes the Sprint 2 behaviour in `ApiClient`.
- Sprint 9 implements the admin projection without a further contract decision.
- #125 alone can establish upload -> transcode -> HLS browser playback; this document proves only the design.

## Addendum (2026-11-19): ADR-012 and D2/D3

- D3 says that no cookie carries a token. [ADR-012](ADR-012.md) D1 adds one cookie, `vod_refresh`, which carries the refresh token, is `HttpOnly` and scoped to `/api/v1/auth`, and is accepted only by the refresh and logout endpoints. No cookie authenticates `/api/v1/*` resources or `/hls/*`; the access token is still accepted only in the `Authorization` header, never in a URL or a cookie.
- D2's recovery is unchanged: the player reads the current access token for every request and joins the shared `ApiClient` recovery. ADR-012 D5 shortens the access-token lifetime to 5 minutes and D6 adds a session check with a revocation delay of at most 30 seconds; both reach the player only through the existing 401 recovery path.
- D2's change of the refresh-failure behaviour (a network error, a timeout or a 5xx keeps the session) moves from Issue 6.6 to Issue 6.9, because the cookie bootstrap needs it; Issue 6.6 reuses it for HLS requests.
- The automated browser smoke in #125 runs after ADR-012's Issue 6.10 and must observe at least one real HLS 401, a successful refresh and a successful retry, instead of inferring them from 60 seconds of media time: the player may play from its buffer, and the JWT clock skew lengthens every token (ADR-012 D5).

## Addendum (2026-11-22): the D2 budget per hls.js load, and terminal HLS load errors (#223)

Owner decisions on 2026-11-22. The author and an independent OpenAI Codex review recommended both separately: first, stopping at once on terminal load errors; second, after four review rounds, running the D2 budget inside a custom hls.js loader.

- **Finding.** D2 assumes that hls.js does not retry a 4xx and that the load-policy `shouldRetry` hook can carry the retry. Neither holds well enough in hls.js 1.7.4:
  - For fragments, or level playlists, of a stream with one level, which every stream here is (ADR-010 D22), hls.js still retries after the hook refuses. When no alternate level or pathway exists, it retries up to `fragLoadPolicy.errorRetry.maxNumRetry` times (6, about 31 seconds of backoff) before the error becomes fatal. This was reproduced in Chromium for a 404 and for a 401 on the D2 retry.
  - Through `xhrSetup` and `shouldRetry`, hls.js does not say which attempts belong to one load. A budget kept per URL either outlives a load or ends inside one. The review reproduced repeated refreshes for one manifest load after stalls.
- **D2 budget per load.** hls.js creates one loader for each playlist or fragment load and calls its `load()` once. The player installs a loader for `pLoader` and `fLoader` (`AuthenticatedHlsLoader`, a subclass of the hls.js `XhrLoader`) that carries the D2 budget of that load:
  - every attempt sends the current access token, only to the same-origin `/hls/video-assets/...` proxy;
  - the first 401 joins the shared `ApiClient` recovery, and the same load sends once more with the recovered token, through the loader's own `loadInternal()`;
  - a 401 on that resend, or a failed recovery, is reported to hls.js as the load's final error, together with the decision. A 401 on the resend ends the session only when the token it sent is still the current one. A refresh rejected with 401 also ends it; a refresh failing by a network error, a timeout or a 5xx keeps it;
  - a transport retry inside the same load, such as the manifest loader's timeout retry, keeps the spent budget;
  - after hls.js aborts or destroys the load, nothing more is sent, even when the recovery settles later.

  A later load of the same playlist or fragment is a new loader with its own budget, for example after a seek or after hls.js gave up a timed-out load and loads it again. A token returned for a late 401 is handled as D2 already handles it for JSON requests.
- **D7 amended.** A manifest, playlist or fragment load error stops loading at once, even when hls.js reports it as non-fatal, in two cases: its status is 404, or the authentication loader ended the load. The player calls `stopLoad()` synchronously in its error listener, which cancels the retry that hls.js has just scheduled. It then applies the D7 mapping:
  - a 404 refetches the playback info once;
  - the loader's decision shows the session-ended state, the network-error state with Retry, or the account-changed state.

  Fatal errors and these terminal load errors share one handling path, so the refetch or the session end runs once. A fatal 401 without a loader decision shows Retry.
- **Unchanged.** Every other non-fatal error is routine and leaves the UI unchanged. 5xx responses, timeouts and network errors keep the hls.js backoff; D4 relies on it for 503 `HLS_STORAGE_UNAVAILABLE`. The backend answers 404 only for an asset that is not current, not visible or not valid, and for a missing object. A 404 is therefore not a transient storage failure.
- **One media recovery per instance.** D7's single `recoverMediaError()` also counts the reset that hls.js 1.7.4 runs by itself for a `ResetMediaSource` action, before any listener sees the error. The player enforces the limit on the instance's method and shows the playback error when a second reset would be needed. Loading restarts at the position from before the detach.
- **Upgrades.** The loader relies on the documented custom-loader options and on the `XhrLoader` subclass contract (`loadInternal`, `abortInternal` and `resetInternalLoader` are protected members in the hls.js typings). The terminal-error handling relies on the listener order and the stream controller's no-alternate retry. Before any hls.js upgrade, unit tests against the real `XhrLoader` and Playwright cases that count requests must pass: exactly one 404 and one playback-info refetch; exactly two sends for a 401 followed by a 401; a fragment 503 retried.
